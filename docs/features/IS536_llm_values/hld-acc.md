# IS536 | HLD ACC — доступ, черновик

План по спеке ACC: ключ доступа в запросе → аккаунт для операции. В v2
логика доступа не меняется; меняются имя — субъект становится
аккаунтом (Д115) — и место ключа на устройстве: он в сборке
приложения, а не в настройках (ACC Ш1, AWP-35, WCL-08), это экранные
планы `hld-awp.md` и `hld-wcl.md`. Операции, которые идут через
доступ, — `hld-lft.md` и `hld-lfl.md`.

## 1. Рамка

- **Цель** — сервер отвечает только тому, у кого есть ключ, и знает,
  кто это: аккаунт с именем и лимитами.
- **Вход и выход** — заголовок `Authorization: Bearer <ключ>` в каждом
  запросе обеих операций; назад — аккаунт в контексте запроса для
  ручки, или 401.
- **Что меняется на сервере** — только имя: `domain.Subject` →
  `domain.Account`, `SubjectByKey` → `AccountByKey`, порт «Субъекты» →
  «Аккаунты», таблица `subjects` → `accounts` и столбец `subject_id` →
  `account_id` в таблицах ключей и расхода, вывод команды
  `lexeme key`, тексты отказов «of account». Логика хука, `Auth` и хранилища как в v1.
  Новая операция `lemmas/from-tokens` идёт через тот же хук: проверку
  ключа генератор ставит на все операции контракта разом.
- **Документы** — спека ACC, [решения](decisions.md) Д47, Д77.

## 2. Схема и код

Схемы слоёв у доступа нет: его две коробки — хук и `Auth` — стоят на
схемах обеих операций. Код как есть, сигнатурами.

```go
// HandleAccessKey — ACC Ш2, первая проверка: сервер зовёт
// её до любой ручки с ключом из заголовка. Ключ из
// заголовка, аккаунт у Auth, аккаунт в контекст. Ошибку не
// мапит: ErrorHandler отдаёт ErrUnauthorized как 401, сбой
// хука не по ключу — 500. Ключ дальше контекста не идёт и
// в логи не пишется (ACC-05, ACC-77). Есть; меняется
// только тип аккаунта.
func (h *wordsHandler) HandleAccessKey(
    ctx context.Context,
    op wordsv1.OperationName,
    key wordsv1.AccessKey,
) (context.Context, error)

// AccountByKey — правило ключа: пустой, неизвестный или
// отозванный ключ — ErrUnauthorized, иначе аккаунт с
// лимитами (ACC-26, ACC-31). Сервис Auth; меняется имя,
// был SubjectByKey.
AccountByKey(
    ctx context.Context,
    key domain.AccessKey,
) (domain.Account, error)

// ByKey — аккаунт по ключу из Postgres; ErrUnauthorized,
// если ключа нет или он отозван. Порт «Аккаунты», были
// «Субъекты»; меняется имя.
ByKey(
    ctx context.Context,
    key domain.AccessKey,
) (domain.Account, error)
```

Выдача и отзыв ключей — команда `lexeme key` и сервис `Keys`, как были
(ACC-31). Поле `daily_limit` у аккаунта остаётся и не читается, пока
лимиты — прокладка (`hld-lim.md`).

## 3. Контракт

Без изменений: схема `accessKey` в `api/openapi.yaml`, ответ 401
`unauthorized` у обеих операций.

## 4. Ключевые решения

- **«Кто ты» и «сколько можно» — разные сервисы** (Д47): `Auth` знает
  способы входа, `Quota` — лимиты; потом сюда же придут Google и
  Telegram.
- **Доступ — сервисная спека** (Д77): операции ссылаются на неё одной
  строкой, тезисы доступа живут здесь.
- **Ключ в сборке** (решение триажа ревью): поля ключа в настройках
  приложения нет, без ключа сценариев снимка и карточки нет.
- **Аккаунт, не субъект** (Д115): кому выдан ключ и у кого считаются
  лимиты; сейчас один на сборку приложения, с входом через Google или
  Telegram — свой у каждого.

## 5. Сквозное

- **401** — только `Auth` через хук, до ручки; ручка про ключ не знает.
- **Секреты** — ключ не попадает ни в логи устройства и сервера, ни в
  тела ответов.
- **Сборка без хука** — ловится интеграционным тестом «запрос без ключа
  → 401».

## 6. Выкатка

- **База данных** — миграция переименования: `subjects` → `accounts`,
  `subject_id` → `account_id` в таблицах ключей и расхода вместе с
  индексом; данные те же.
- **Ключи** — новых нет, ключ в сборке приложения тот же, что сейчас.
- **Конфиг** — `LLM_SUBJECT_DAILY` → `LLM_ACCOUNT_DAILY`, `hld-lim.md`.

## 7. Риски

- **Один ключ на всё приложение** — учёт и лимиты идут по одному
  аккаунту; отзыв ключа останавливает всех.
