# IS523 | Схема получения значений слова (2026-10-06)

Путь одного слова от распознанного текста до карточки на экране: что
делает устройство, что сервер, что нейронка, какие данные ходят между ними
и что происходит при отказах. Опирается на решения брифа Д4, Д7, Д8, Д13,
Д14–Д17 и на пробы из `research_surface.md`.

Статус: схема согласована на словах, открыт один выбор (§6). Код не
начат.

## 1. Участники

- **Устройство** — загружает страницы источников, сжимает их до текста,
  собирает запрос, показывает карточку, пишет в словарь.
- **Бэкенд** (свой, Д13) — принимает запрос с токеном юзера, ходит в
  OpenRouter, возвращает JSON на слово. Ключ OpenRouter, промпт и модель
  живут здесь.
- **OpenRouter** — выбирает значение по контексту, заполняет параметры
  каталога из фрагментов источников, отдаёт структурированный ответ по
  JSON-схеме.
- **Источники** — Wiktionary как основное ядро для всех языков (REST без
  ключа); ссылки юзера (Cambridge и любые другие) как дополнительные;
  память нейронки как последний источник.

## 2. Шаги

### 2.1. Устройство: загрузка страницы источника

- Для каждого отмеченного слова и каждого источника в порядке, который
  юзер выбрал при запуске (Д15): адрес собирается из шаблона источника,
  слово подставляется в адрес. Правило подстановки — часть шаблона:
  у Cambridge дефис (`break-down`), у Wiktionary подчёркивание
  (`break_down`).
- Запрос через OkHttp с браузерным User-Agent, с редиректами, с таймаутом.
  Пробы: Cambridge отвечает 200 на UA `okhttp/4.12.0` и на UA Chrome;
  без браузерного UA часть словарей отдаёт 403 (грабли из скилла
  dict-fetch).
- Код 200 не значит «статья найдена»: при промахе словари отдают
  страницу поиска или «spellcheck». Признак статьи проверяется по
  содержимому (см. 2.2); при промахе источник для этого слова
  пропускается.
- Ответ страницы кешируется на устройстве (личная копия юзера) на время
  сессии импорта, чтобы повтор запроса не ходил в сеть.

### 2.2. Устройство: сжатие страницы до текста

Страница Cambridge — 270–370 КБ HTML; текст статьи после снятия разметки
— 1–2 тыс. токенов. На сервер уходит текст, не HTML.

Два вида сжатия (выбор — §6):

- **Общее извлечение текста**: снять скрипты, стили, меню, подвал,
  оставить основной текст (библиотека Readability4J или свой аналог). Не
  знает о сайте, не ломается при смене вёрстки, может захватить лишнее.
- **Разбор по вёрстке**: селекторы или регулярки под конкретный сайт
  (как `parse-cambridge.pl` в скилле dict-fetch). Точные поля, токенов в
  разы меньше, ломается при смене классов — грабли скилла это
  подтверждают (класс с пробелом на конце, вложенный `span` в
  транскрипции).

Признак промаха для общего извлечения: текст короче порога или не
содержит слова; для разбора по вёрстке — не нашёлся ни один блок
значения.

### 2.3. Устройство → бэкенд: один запрос на слово

```json
{
  "word": "break down",
  "context": "The car broke down on the way to the airport.",
  "learningLanguage": "en",
  "translationLanguage": "ru",
  "parameters": ["translation", "definition", "partOfSpeech",
                 "example", "transcription", "level", "countability"],
  "descriptions": {
    "myComponent42": "описание юзера для нейронки, если компонент без параметра каталога (Д14)"
  },
  "sources": [
    { "id": "wiktionary", "text": "…текст статьи…" },
    { "id": "user-link-1", "text": "…текст статьи…" }
  ]
}
```

- `parameters` — только то, что юзер отметил при запуске (Д15), из
  каталога для языка словаря (Д14).
- `descriptions` — свободные описания компонентов без параметра каталога;
  работают только с нейронкой (Д14).
- Заголовок `Authorization: Bearer <токен юзера>` (Д17).
- Размер запроса: по 1–2 тыс. токенов на источник плюс контекст.

### 2.4. Бэкенд → OpenRouter

- Промпт с задачей: по контексту выбрать значение слова; для каждого
  запрошенного параметра дать значение и указать источник (`sourceId`)
  или пометить `"fromModel": true`, если взято из памяти модели.
- Ответ требуется по JSON-схеме (структурированный вывод OpenRouter);
  при ответе не по схеме — один повтор.
- Модель и промпт — на сервере (Д13), меняются без релиза приложения.
- Бэкенд фрагменты источников не сохраняет; в логах — размеры, время,
  модель, стоимость. Ограничения условий Cambridge — в
  `research_surface.md` §3а; что из них применимо к текущей ситуации,
  решает юзер.
- Лимиты: на токен юзера в сутки и общий потолок; на ключе OpenRouter —
  потолок кредитов (Д17).

### 2.5. Бэкенд → устройство: JSON на слово

```json
{
  "word": "break down",
  "lemma": "break down",
  "sense": "перестать работать (о машине, механизме)",
  "parameters": {
    "translation":   { "value": "сломаться", "sourceId": "user-link-1" },
    "definition":    { "value": "to stop working", "sourceId": "wiktionary" },
    "partOfSpeech":  { "value": "phrasal verb", "sourceId": "wiktionary" },
    "example":       { "value": "The car broke down…", "sourceId": "context" },
    "transcription": { "value": "/breɪk daʊn/", "sourceId": "user-link-1" },
    "level":         { "value": "B1", "fromModel": true },
    "countability":  null
  },
  "descriptions": {
    "myComponent42": { "value": "…", "fromModel": true }
  },
  "otherSenses": ["расплакаться", "разложить на части"],
  "sourcesUsed": ["wiktionary", "user-link-1"],
  "sourcesEmpty": []
}
```

- `null` у параметра — ни один источник и модель не дали значения.
- `otherSenses` — на случай, если контекст выбран неверно: юзер может
  переключить значение на экране (следствие Д10, уточнить в подфиче 6).

### 2.6. Устройство: карточка и добавление

- Карточка слова со всеми полученными параметрами и пометкой источника у
  каждого.
- Параметр с привязанным компонентом словаря (Д16) ложится в него по
  умолчанию; параметр без компонента показывается, но по умолчанию не
  добавляется (Д8); юзер может выбрать компонент вручную (Д7).
- Для CHOICE-компонентов (исчисляемость, род) нужно соответствие
  «значение каталога → опция компонента юзера» — открытый вопрос брифа
  подфичи «Каталог параметров слова» (Д16).
- Юзер отмечает, что добавить, и подтверждает; слово с лексемой пишется
  в словарь. Можно не добавлять ничего.

## 3. Отказы и деградация

Что случилось → что делает схема.

- **Источник не ответил, 403/429, таймаут** → источник пропущен для
  этого слова, идёт следующий по порядку; в карточке пометка «источник
  не ответил».
- **Код 200, но страница поиска вместо статьи** → то же, по признаку
  промаха из 2.2.
- **Сайт сменил вёрстку** → общее извлечение продолжает работать
  (возможен лишний текст); разбор по вёрстке отдаёт пустоту и виден как
  «источник пуст» на каждом слове, правило надо править.
- **Нейронка ответила не по схеме** → один повтор; затем карточка
  «нейронка не ответила», слово можно добавить голым.
- **Ни один источник ничего не дал** → карточка с пометкой «источники
  пусты», параметры из памяти модели помечены `fromModel`.
- **Токен юзера отозван или лимит исчерпан** → бэкенд отвечает 401/429,
  приложение показывает причину, импорт останавливается.
- **Нет сети на устройстве** → загрузка и запрос не начинаются, список
  слов (Д10) остаётся, импорт можно повторить.

Сигнал поломки разбора по вёрстке, если он выбран: контрольное слово
(например, `negotiate` у Cambridge) с ожидаемыми полями; проверка
запускается при старте импорта, пустой результат сообщается юзеру до
обработки всех слов.

## 4. Где живут правила источников

Вариант → что меняется при смене вёрстки или адреса.

- **Правила в коде приложения** → релиз в Play; до релиза источник молча
  пуст.
- **Правила конфигом с бэкенда** → правка конфига на сервере, без
  релиза.
- **Правил нет, общее извлечение + нейронка** → менять нечего; меняется
  только шаблон адреса, он у юзера в настройках источника.

Шаблон адреса источника (Д4): юзер даёт ссылку на страницу одного слова,
приложение выводит из неё шаблон (слово в пути → подстановка), правило
слога (дефис / подчёркивание / `+`) — часть шаблона.

## 5. Соответствие подфичам

- Токен, канал, лимиты (заголовок в 2.3, лимиты в 2.4) — подфича 2
  «Бэкенд и шлюз».
- Слова и контекст из фото — подфичи 3 «Захват фото» (IS527) и 4
  «Распознавание и список слов».
- Загрузка, сжатие, запрос, ответ (2.1–2.5) — подфича 5 «Источники
  значений».
- Карточка, компоненты, добавление (2.6) — подфича 6 «Окно добавления».
- Шаблоны адресов, порядок источников (§4) — подфича 7 «Управление
  источниками»; часть — в 5 для Wiktionary и одной ссылки юзера.
- Каталог параметров, привязка компонентов — новая подфича «Каталог
  параметров слова» (Д14, Д16).

## 6. Открытый выбор: вид сжатия на устройстве в первой версии

1. Общее извлечение текста (Readability4J) + нейронка. Не зависит от
   вёрстки, работает с любой ссылкой юзера; 1–2 тыс. токенов на слово и
   источник.
2. Селекторы под сайт конфигом с бэкенда; нейронка только выбирает
   значение. Токенов в разы меньше, поля точные; свой конфиг на каждый
   сайт, при редизайне правится конфиг без релиза.
3. Селекторы в коде приложения (как в скилле dict-fetch). Дешевле всего;
   при редизайне ждёт релиза.

Варианты 1 и 2 совместимы: конфиг под сайт — ускорение поверх общего
извлечения, при пустом результате конфига откат на общее извлечение.

## 7. Не проверено

- Readability4J на страницах Cambridge и Wiktionary: сколько лишнего
  текста остаётся, не теряются ли примеры и транскрипция.
- Структурированный вывод OpenRouter на выбранной модели: доля ответов
  не по схеме.
- Поведение Cambridge при десятках запросов подряд с одного устройства
  (проба была на одиночных запросах).
- Wiktionary REST для не-английских слов: какие поля отдаёт (род и
  транскрипцию — нет, см. research_surface.md), нужен ли разбор
  викитекста или выгрузка Kaikki на бэкенде.
