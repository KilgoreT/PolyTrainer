# IS523 | Бриф: слова из текста (фото / файл → словарь)

Issue: https://github.com/KilgoreT/PolyTrainer/issues/523
Ветка: `IS523_words_from_text` (от master `8fd0e508`).
Источник: идея юзера (2026-10-05). Фича крупная — делится на подфичи по
итогам обсуждения этого брифа.

## Идея

Юзер даёт приложению фото текста, скриншот или файл. Приложение:

1. переводит картинку / файл в чистый текст;
2. выделяет из текста все значимые слова;
3. для каждого слова сходит в онлайн-словари: перевод, определение,
   часть речи, грамматические параметры, примеры;
4. показывает набор слов с готовыми лексемами — юзер выбирает, что и как
   добавить в словарь.

## Флоу юзера (как описал юзер)

1. Кнопка запуска — видимо, на табе «Словарь»; возможно, FAB делится на
   несколько действий (мнения пока нет).
2. Выбор источника: файл или фото текста.
3. Файл уходит в нейронку (OpenRouter).
4. Возвращается набор слов с готовыми лексемами. Слова и лексемы, которые
   уже есть в словаре, помечены индикацией.
5. Юзер выбирает слова для добавления; возможно — сразу в группу.
6. Юзер выбирает значения (лексемы) каждого слова: пришло 4 — может взять
   одно.
7. Юзер видит, какое значение использовано в тексте, если их несколько.
8. Вместе со значением — примеры для добавления: из присланного текста или
   из словарей.
9. Словари-источники по языкам: для английского у юзера в приоритете
   Cambridge; для других языков — определить. Выбирает нейронка сама или
   юзер предустанавливает — обсуждаемо.

## Что есть в проекте (факты, 2026-10-05)

- **Сети нет.** Ни Retrofit/OkHttp/Ktor, ни своего `INTERNET` в манифестах
  (приходит транзитом от Firebase). Всё сетевое — с нуля: клиент, таймауты,
  ошибки, офлайн.
- **Ключей нет.** Нет механизма секретов (`local.properties` / BuildConfig
  для API-ключей).
- **У словаря нет языка.** `DictionaryDb`: `numericCode` (страна → флаг),
  `name`. Язык выводится из страны (`CountryProvider.getLanguagesForCountry`
  — список, может быть несколько). **Родной язык юзера (язык перевода) нигде
  не хранится.** Для «перевода» и выбора словаря-источника нужны оба.
- **Куда класть данные из словарей** (модель лексемы, IS481/486/491/515):
  - перевод → встроенный `TRANSLATION`;
  - часть речи → встроенный CHOICE `PART_OF_SPEECH` (12 опций, IS515);
  - пример → встроенный `EXAMPLE` (CAPTIONED_TEXT, multiple; caption —
    подпись, например источник);
  - определение → **пользовательский** пословарный тип «Definition» — в
    конкретном словаре его может не быть;
  - грамматика (род, число, форма глагола…) → пользовательские CHOICE;
    иерархию признаков юзер ещё строит (см. Backlog, IS511 follow-up).
- **Группы** есть (IS493) — добавление «сразу в группу» ложится на готовое.
- **Прецедент получения словарных данных:** у юзера есть скилл
  `dict-lookup` (Cambridge / Oxford Learner's / Longman через скрипт) — формат
  карточки и выбор источников можно взять оттуда.

## Предложения (к обсуждению)

### П1. Распознавание текста — на устройстве, не нейронкой

Для фото/скриншота — ML Kit Text Recognition v2 (бесплатно, офлайн,
быстро). Нейронка получает уже текст.
**Почему:** картинка в мультимодальную модель — в разы дороже и медленнее,
чем текст; OCR печатного текста ML Kit делает надёжно.
**Ограничение (сверено с документацией ML Kit, 2026-10-05):** на устройстве
поддержаны только письменности: латиница (английский, испанский,
французский, немецкий и десятки других), китайская, японская, корейская,
деванагари (хинди и др.) — каждая отдельной библиотекой. **Кириллица,
греческий, арабский, иврит, тайский НЕ поддержаны.** Для них — либо
картинка в мультимодальную модель, либо сторонний OCR (PaddleOCR,
Tesseract).
**Риск качества:** рукописный текст, многоколоночная вёрстка (путается
порядок чтения), смазанные и тёмные фото — хуже.
Файлы: `.txt` — сразу текст; PDF / DOCX — отдельное решение (объём, парсинг).

### П2. Нейронка — для того, что умеет только она

- выделить значимые слова → **леммы** (went → go), выкинуть служебные,
  имена, числа; фразовые глаголы и устойчивые выражения — целиком;
- для каждого слова — предложение из текста, где оно стоит (контекст);
- **какое значение использовано в тексте** (пункт 7) — выбор среди
  значений из словаря по контексту.

### П3. Значения — из словарей, а не из нейронки

Перевод/определение/примеры брать из словаря-источника, нейронке —
только сопоставить контекст со значением.
**Почему:** нейронка правдоподобно выдумывает значения и примеры; словарь —
источник истины (для юзера это принципиально: «как у больших и умных
ребят», см. IS515).
**Возражение к себе / риск:** у Cambridge, Oxford, Longman нет бесплатного
публичного API; скрейпинг сайтов из мобильного приложения — нарушение их
условий и хрупкость (вёрстка меняется). Варианты:
- платные API (Oxford Dictionaries API, Cambridge API — по договору);
- бесплатные открытые: Wiktionary / Free Dictionary API, Merriam-Webster
  (бесплатный ключ, некоммерческий лимит);
- нейронка с веб-поиском (OpenRouter `:online`) — берёт данные со
  словарных сайтов сама, со ссылкой на источник;
- гибрид: открытый словарь + нейронка как фоллбэк, с пометкой источника.

### П4. Ключ OpenRouter — не в APK

Ключ, зашитый в приложение, извлекается из APK за минуты → чужие запросы за
счёт юзера. Варианты:
- **свой ключ юзера** (BYOK) — вводится в настройках, хранится в
  EncryptedSharedPreferences / Keystore; ноль серверной инфраструктуры;
  подходит, пока приложение для себя и тестеров alpha;
- **свой бэкенд-прокси** — ключ на сервере, лимиты, кэш словарных ответов;
  нужен, если фича для всех пользователей Play.

### П5. Дубли — сравнение по лемме

«Уже есть в словаре» — по лемме и словарю (без регистра, trim); для слова,
которое есть, — показать, какие его значения уже есть, а какие новые
(пункт 4 флоу на уровне лексем, а не только слов).

### П6. Приватность

Текст юзера уходит третьей стороне (OpenRouter → провайдер модели). Нужны:
явное согласие при первом использовании, обновление политики
конфиденциальности и формы Data safety в Play.

## Решения

- **Д1 (2026-10-05). [Пересмотрено — см. Д13: тонкий бэкенд сразу.]** Ключ:
  сначала свой ключ юзера (BYOK), со слоем под будущий бэкенд. Сейчас — для юзера и alpha-тестеров: ключ OpenRouter
  вводится в настройках, хранится зашифрованно (Keystore). Все вызовы модели
  и словарей — через интерфейс-шлюз в домене; реализация «напрямую в
  OpenRouter» сейчас, «через свой бэкенд» — потом, без переделки экранов.
  Целевое состояние (юзер): фича для всех пользователей Play — вход через
  Google-аккаунт, лимиты, платежи, тарифы.
  Следствия на будущее (не в этой фиче): цифровые услуги в Play — через Play
  Billing; лимиты и учёт расхода — только на сервере; бэкенд (аккаунты,
  расход, проверка покупок) — отдельный проект.

- **Д2 (2026-10-05). Распознавание — на устройстве (ML Kit), нейронке —
  текст.** Юзер: «давай попробуем, позже проверим» — качество оцениваем на
  практике. Допущение первой версии (моё, юзер может отменить): фото
  работает для письменностей ML Kit (латиница, китайская, японская,
  корейская, деванагари); для остальных (кириллица, греческий, арабский и
  др.) фото недоступно, текст вводится вставкой или файлом. Фоллбэк
  «картинка в мультимодальную модель» для неподдержанных письменностей и
  плохих фото — отдельной подфичей позже; шлюз из Д1 это позволяет.
  Перед распознаванием юзер видит и может поправить распознанный текст.
  **Решение предварительное.** Отдельная задача-исследование (юзер,
  2026-10-05, «потом»): сколько стоят разные модели OpenRouter на
  распознавании и насколько они лучше ML Kit; по итогам Д2 пересматривается.
- **Д3 (2026-10-05). Источники первой версии — только фото:** с камеры и
  из галереи (в т.ч. скриншоты). Файлов (`.txt`, PDF, DOCX) и вставки
  текста нет. Следствие для Д2: для письменностей вне ML Kit (кириллица,
  греческий, арабский и др.) фича в первой версии недоступна целиком —
  запасного ввода текстом нет; закрывается фоллбэком на мультимодальную
  модель или решением исследования из Д2.
- **Д4 (2026-10-05). Значения — из словарей с первой версии, не «из головы»
  нейронки.**
  - Из коробки — открытые словари (Wiktionary / Free Dictionary API:
    бесплатно, структурированно; лицензия CC BY-SA — нужна ссылка на
    источник).
  - **Свои источники юзера (идея юзера):** юзер даёт ссылку на страницу
    словаря с конкретным словом (например, страницу Cambridge для
    `interact`); приложение выводит из неё шаблон (слово → подстановка) и
    по нему открывает страницы остальных слов; нейронка разбирает страницу
    в структуру (перевод, определение, часть речи, примеры). Источники
    задаются по языкам (пункт 9 флоу).
  - **Веб-поиск нейронкой** — обсуждаем после оценки стоимости; цена
    входит в исследование из Д2.
  - Следствие: словари-источники входят в первую версию (см. нарезку).
  - Риски (в исследование): (а) сайты вроде Cambridge защищены от ботов и
    запрещают автоматический доступ — запросы приложения могут
    блокироваться; пока страницу запрашивает устройство юзера по его
    ссылке, позиция мягче, но при переносе на бэкенд это уже массовый
    сбор; (б) цена: каждое слово = загрузка страницы + разбор нейронкой
    (тысячи токенов на слово) — заметно дороже ответа «из головы»;
    (в) шаблон ссылки: фразовые глаголы и словосочетания (`break down` →
    `break-down`) у каждого сайта свои правила.
- **Д5 + Д6 (2026-10-05). У словаря — пара языков: изучаемый и язык
  перевода** (новые поля, миграция БД).
  - **Язык перевода** — по умолчанию язык телефона; можно поменять.
  - **Изучаемый язык** — при выборе флага подставляется основной язык
    страны (первый в списке библиотеки флагов); юзер выбирает из языков
    страны (идея юзера). Данные есть: `country-data` отдаёт языки с кодами —
    `"English (en-US)"`; у 247 стран из 250 ≥ 1 языка (без языка —
    Антарктида, Буве, Херд), у 70 — ровно один, у 177 — несколько (до 26).
    Уточнено полным прогоном массива 2026-10-05 (см. план IS525, 1.1).
  - Список не жёсткий (юзер согласен): языки страны сверху + выбор не
    только из языков страны («Другой язык…»; флаг ≠ язык: латынь,
    эсперанто, флаг «для красоты»).
  - Языковые семьи в списках библиотеки («Caucasian languages», «Altaic
    languages») **не фильтруем** (юзер: не мешают, с основными не
    пересекаются) — список страны показываем как есть.
  - У существующих словарей языки заполняются автоматически (основной язык
    страны флага + язык телефона); **оба языка можно исправить в
    редактировании словаря** (требование юзера).
  - Допущение (моё): названия языков показываем на языке интерфейса (из
    кода, средствами Android), а не английские из библиотеки.
- **Д7 (2026-10-05). Куда класть данные — выбирает юзер в окне добавления
  списка слов; по умолчанию — в «Перевод», даже если это определение**
  (юзер: полем перевода можно пользоваться как угодно).
  - В окне добавления — блок соответствий «что добавляем → в какой
    компонент». Для каждого вида данных юзер может: выбрать другой
    компонент словаря, отменить добавление этого вида данных, создать
    компонент специально под него.
  - Допущения (мои, юзер может отменить):
    (а) соответствие задаётся на весь список, не на каждое слово, и
    запоминается для словаря до следующего раза;
    (б) в выборе — только совместимые компоненты (текст → текстовые; часть
    речи → встроенный CHOICE; пример → встроенный «Пример»);
    (в) **«Перевод» по умолчанию хранит одно значение на лексему**
    (`is_multiple = 0`): когда у значения есть и перевод, и определение, в
    «Перевод» идёт перевод, а определение по умолчанию не добавляется, пока
    юзер не выберет или не создаст для него компонент; когда перевода нет
    (одноязычный источник) — в «Перевод» идёт определение.
- **Д8 (2026-10-05). Из словарей берём всё и всё показываем на странице со
  словами** (перевод, определение, часть речи, примеры, транскрипция,
  грамматика и прочее, что даёт источник).
  - Дополнительные данные (сверх перевода / определения / части речи /
    примера) по умолчанию **не добавляются**; юзер может выбрать для них
    существующий компонент словаря.
  - **Создание компонента прямо из окна добавления — следующей итерацией**
    (уточнение к Д7): в первой версии в окне только выбор существующего
    компонента или «не добавлять»; новый компонент создаётся как сейчас —
    в «Компонентах словаря».
  - Допущение (моё, юзер может отменить): виды данных с устойчивым
    названием (транскрипция, формы слова, грамматические пометки, уровень)
    получают строку в блоке соответствий; всё прочее, что источник отдаёт
    в свободной форме, в первой версии только показывается — у таких
    данных название от слова к слову разное, соответствие не запомнить.
- **Д9 (2026-10-05). Вход — маленькая кнопка с камерой над основной «+»**
  на вкладке «Словарь». Добавление слова остаётся в одно нажатие.
  Допущения (мои): кнопка видна только на внутренней вкладке «Слова» (не на

- **Д10 (2026-10-05). Значения загружаются в два шага.** Сначала быстрый

  юзер отмечает нужные; значения из словарей загружаются только для

  Допущения (мои): слова — в порядке появления в тексте; слова, которые

- **Д13 (2026-10-05). Пересмотр Д1 и Д11: тонкий бэкенд сразу.**
  Приложение ходит только на свой бэкенд, бэкенд — в OpenRouter. Этапа
  «свой ключ юзера в настройках» нет.
  - Бэкенд тонкий: несколько адресов (выделить слова из фото или текста;
    разобрать словарную статью), ключ OpenRouter, промпты и выбор модели —
    на сервере (правятся без релиза в Play), доступ по токенам для юзера и
    тестеров. Вход через Google, лимиты, учёт расхода, тарифы — потом.
  - Следствия: экран ввода ключа и поле модели в настройках (Д1, Д11) не
    делаются; бэкенд — отдельный проект (сервер, хостинг, развёртывание),
    первая сквозная версия зависит от него; подфичи 4 и 5 состоят из
    серверной части (адрес + промпт) и клиентской.
  - Допущение (моё, юзер может отменить): словарные страницы загружает
    телефон (с адреса юзера сайты отвечают — проверено), на бэкенд уходит
    уже текст статьи; массовую загрузку страниц с сервера не делаем.

## Исходные вопросы

- **Д1. Ключ OpenRouter.** Свой ключ юзера в настройках (BYOK) или свой
  бэкенд-прокси? Для кого фича: только для тебя и alpha-тестеров или для
  всех пользователей Play?
- **Д2. Распознавание.** OCR на устройстве (ML Kit) + нейронка для текста,
  или всё отдать мультимодальной модели?
- **Д3. Форматы файлов.** Только фото/скриншот + `.txt`, или сразу PDF /
  DOCX / EPUB?
- **Д4. Откуда значения.** Словарные API (какие), нейронка с веб-поиском,
  или нейронка «из головы» с пометкой «требует проверки»?
- **Д5. Язык перевода.** Где хранить родной язык юзера: глобальная
  настройка или поле словаря («с какого на какой»)?
- **Д6. Язык словаря.** Добавить словарю явный язык или выводить из страны
  (у страны бывает несколько языков)?
- **Д7. Определение.** Если в словаре нет пользовательского типа
  «Definition» — создавать его автоматически, спрашивать или пропускать
  определения?
- **Д8. Грамматика.** Какие грамматические параметры тянуть сейчас (только
  часть речи?) с учётом того, что иерархию признаков юзер ещё строит?
- **Д9. Вход в фичу.** FAB с выбором действий (добавить слово / из
  текста), отдельная кнопка в аппбаре, или пункт меню?
- **Д10. Объём.** Лимит слов за один запрос (длинный текст = сотни слов,
  стоимость и время), стриминг результата по мере готовности?
- **Д11. Модель.** Какую модель OpenRouter по умолчанию; даём ли юзеру
  выбрать модель?
- **Д12. Флоу разработки.** Подфичи — отдельными issue/ветками/релизами
  или одна ветка с этапами?
