# Конкуренты mate — обзор ландшафта

Исследование 2026-08-31 (веб-сверка + анализ). Вопрос: кто уже есть в
нише Kotlin TEA/MVI-раннеров, чем они лучше/хуже планируемого mate
([mate_analysis.md](mate_analysis.md)), и где реальная ниша.

Оси сравнения — из нашей планки:
1. чистый reducer `Msg × State → (State, Effects)`;
2. эффекты как ДАННЫЕ (не императивный код);
3. декларативные подписки из State (elm-овский Sub);
4. навигация как данные в комплекте;
5. сценарные тесты уровня ВСЕГО приложения;
6. зрелость/инструменты/комьюнити.

## Разбор по библиотекам

### MVIKotlin (Arkadii Ivanov / Badoo) — самый зрелый

**Архитектура:** Store = Reducer (чистый!) + Executor + Bootstrapper.
Intent → Executor → Message → Reducer → State; side effects — Labels.

**Сильное:** мультиплатформенность выверена годами; **time-travel
прямо в IDE-плагине** (запись/воспроизведение Msg — то, к чему наш
MateObserver только фундамент); логгер-обёртки store; экосистема —
Decompose (навигация) + Essenty (lifecycle); много продакшена, доки,
сэмплы.

**Слабое (для нашей планки):** **Executor — императивный код**, не
эффекты-данные: «что сделать» решается кодом executor'а, а не
описывается значением из reducer'а. Следствия: сравнить/заассертить
намерение нельзя, интеграционный тест = мокать executor целиком;
elm-полнота теряется в самом важном месте. Подписки императивные
(executor подписывается сам). Навигация — отдельная библиотека
(Decompose), другая парадигма (компонентные деревья, не эффекты).

**Чему учиться:** time-travel UX; протокол store-логгеров; как
оформлены сэмплы и migration-гайды.

### Orbit MVI — самый «лёгкий вход»

**Архитектура:** MVVM+: `intent { reduce { state.copy(...) };
postSideEffect(...) }` — всё в корутинных лямбдах контейнера.

**Сильное:** порог входа минимальный; в проде с 2019, 130+ открытых
использований; тестовая обвязка для контейнеров.

**Слабое:** это НЕ TEA вообще: reducer'а как чистой функции нет —
изменения state разбросаны по intent-лямбдам; эффекты — канал
одноразовых событий (антипаттерн с точки зрения нашей О5-очереди:
события теряемы); каузальность/replay невозможны в принципе.

**Чему учиться:** простоте README («пять минут до первого экрана») —
у mate с его принципами есть риск отпугнуть вводной сложностью.

### FlowMVI (nek12) — самый быстрорастущий

**Архитектура:** state-machine поверх Flow; плагинная система
(onIntent/onState/декораторы) — идейный родственник нашего
MateObserver, но плагины могут и ВМЕШИВАТЬСЯ (middleware), не только
наблюдать.

**Сильное:** DX и документация — образцовые; активная разработка;
KMP; автор ведёт то самое сравнение 17 библиотек — понимает ландшафт.

**Слабое:** reducer'ы — императивные suspend-обработчики в
PipelineContext (state меняется методами, не возвратом значения);
эффекты не данные; подписок-деклараций нет.

**Чему учиться:** структуре доков и плагинной композиции (наш observer
+ политика ошибок могут вырасти в похожую точку расширения — но
осознанно только read-only, вмешательство ломает детерминизм).

### Ballast (Copper Leaf) — самый «всё-в-одном»

**Архитектура:** Redux-style discrete Inputs + suspend InputHandler +
sideJob'ы; аддоны: навигационный роутер, undo/redo, **debugger-app**
(отдельное десктоп-приложение смотрит state/inputs живого приложения).

**Сильное:** единственный из MVI-мира, кто довёл РОУТИНГ ДО ДАННЫХ
(Ballast Navigation: route-таблица) — валидация нашей идеи navGraph;
debugger-app — красивая витринная фича; вменяемые гайды.

**Слабое:** InputHandler императивен; sideJob'ы — управление
корутинами руками; роутер — аддон со своей моделью, не эффекты
раннера; комьюнити маленькое (bus factor сравним с нашим).

**Чему учиться:** Ballast Navigation (сверить нашу navGraph-модель с
их route-matching'ом); идея debugger-app поверх MateObserver.

### Mobius (Spotify) — идейно ближайший, но спящий

**Архитектура:** честный TEA: `Update(model, event) → Next(model,
effects)` — ЧИСТАЯ функция, **эффекты — данные**, исполняют
EffectHandlers; Init как first-class.

**Сильное:** та же элм-родословная, что у mate — подтверждение, что
«эффекты-данные в проде на больших приложениях» работает (Spotify);
проверенные паттерны тестирования Update.

**Слабое:** Java-first API, RxJava-наследие, **не KMP**; развитие
фактически заморожено; подписок из Model нет (EventSources —
статические источники, задаются при сборке loop'а, не выводятся из
state); навигации нет; тестирование — по одному loop'у.

**Чему учиться:** формулировкам их доков про «pure update /
effect handlers» (лучшие тексты об эффектах-данных); граблям из
issue-трекера.

### Elmslie (vivid.money) — русская TEA

**Архитектура:** TEA: чистый reducer, эффекты-данные, Actor'ы
(исполнители эффектов), поддержка вложенности компонентов.

**Сильное:** ближайший к mate живой родственник по идеологии;
продакшен vivid.money; v3 на корутинах.

**Слабое:** Android-only (не KMP); маленькое комьюнити; подписки
императивные (через эффекты — ровно наша сегодняшняя О2-боль);
навигации и app-тестов нет.

**Чему учиться:** их опыт «TEA в бою»: что в API оказалось неудобным
(история изменений v1→v3 — бесплатные уроки).

### За кадром (смежные ниши)

- **Decompose/Essenty** — не MVI: KMP-навигация компонентными
  деревьями, конкурент mate-navigation по нише, но императивная
  модель; сильна в back-stack/lifecycle-тонкостях — сверяться при
  реализации интерпретатора.
- **Circuit (Slack)** — presenter-as-Composable + навигация; не TEA
  (state производится композицией), но эталон по тестам presenter'ов
  и «архитектура целиком».
- **ReduxKotlin/ReKotlin/Teapot/RxElm** — мертвы или заморожены;
  подтверждение, что ниша «чистый TEA на Kotlin» много раз
  начиналась и бросалась — довести до конца само по себе отличие.

## Уникальность mate (честная)

Сочетание, которого нет НИ У КОГО из списка:

1. **Полный Elm-цикл в KMP:** чистый reducer + эффекты-данные (есть
   только у не-KMP Mobius/Elmslie) + **декларативные подписки из
   State** — их нет вообще ни у кого, все живут императивным
   subscribe/unsubscribe.
2. **Навигация как данные родной моделью** (эффект → navGraph →
   интерпретатор), а не соседней библиотекой/аддоном.
3. **Сценарный харнес всего приложения** (все Mate + живая навигация +
   стабы use case'ов, JVM, трасса при падении) — у ВСЕХ конкурентов
   тестирование заканчивается на одном store/loop за раз. Это главный
   кандидат в killer-фичу и одновременно самое смелое обещание.
4. Философия строгости: П1 (различимые намерения), политика ошибок,
   громкие fail'ы конфигурации.

## Где конкуренты объективно сильнее

1. **Зрелость:** годы продакшена, выверенные edge cases, сотни
   пользователей — у mate ноль; первые баги ловить нам.
2. **Инструменты:** time-travel IDE (MVIKotlin), debugger-app
   (Ballast), плагины (FlowMVI) — у mate только фундамент
   (MateObserver) без тулинга.
3. **Доки/комьюнити/сэмплы** — у mate предстоит с нуля.
4. **Bus factor:** у mate = 1 (у Ballast/Elmslie, впрочем,近 тоже).

## Позиционирование

Не «убийца MVIKotlin»: побеждать зрелость лоб-в-лоб бессмысленно.
Позиция mate: **эталонная TEA-библиотека для собственных проектов и
витрина** — единственная с полным Elm-циклом (включая подписки) в KMP
и единственная со сценарными тестами уровня приложения. Уникальность
не выдуманная — подтверждена сверкой по осям. Довести до Э7 —
уже отличие от кладбища брошенных Kotlin-TEA.
