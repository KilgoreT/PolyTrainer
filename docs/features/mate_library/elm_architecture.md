# Принципы TEA (The Elm Architecture)

Эталон для сверки mate ([brief](brief.md), анализ —
[mate_analysis.md](mate_analysis.md)). Здесь — ПРИНЦИПЫ, не синтаксис
Elm; терминология Elm сохранена, в скобках — привычные аналоги.

## 1. Три части

```
Model  — ВСЁ состояние приложения (одна иммутабельная структура)
View   — чистая функция Model → UI
Update — чистая функция Msg × Model → (Model, Cmd Msg)
```

Цикл однонаправленный: UI порождает Msg → update считает новую Model и
команды → runtime применяет Model (перерисовка) и исполняет Cmd →
результаты Cmd возвращаются НОВЫМИ Msg → цикл.

## 2. Model — единственный источник истины

- Одна структура на программу. В Elm программа — ВСЁ приложение
  (SPA целиком: страницы — варианты внутри одной Model, роутинг — тот
  же update); в mate естественная единица — экран, это осознанное
  отступление от эталона. Никакого состояния вне Model — всё, что
  влияет на рендер или решения update, лежит в ней.
- Иммутабельность: update не мутирует, а строит новую Model.
- Из Model должно быть ВЫВОДИМО всё поведение: рендер (View), активные
  подписки (см. §5), допустимость действий (guard'ы).

## 3. Update — чистая тотальная функция

- `update : Msg -> Model -> (Model, Cmd Msg)` — никаких side effects:
  ни IO, ни времени, ни рандома, ни глобалов. Одинаковый вход →
  одинаковый выход, всегда.
- Тотальность: update обязан обработать ЛЮБОЙ Msg в ЛЮБОМ состоянии.
  Компилятор Elm гарантирует лишь покрытие всех КОНСТРУКТОРОВ Msg
  (исчерпывающий case); корректный no-op для Msg, невозможного в
  текущем состоянии, — дисциплина автора update, матрицу Msg×State
  никто не enforce'ит.
- Msg — факты («что произошло»), не команды («что сделать»): кнопка
  нажата, ответ пришёл, тик случился. Это рекомендация зрелого
  Elm-сообщества (официальный гайд спокойно пишет Increment/Decrement) —
  для mate принимаем как принцип.
- В Elm нет runtime-исключений: ошибки — значения (Result/Maybe),
  приходят обычным Msg; update не может «упасть». Тотальность опирается
  и на это (для Kotlin-раннера — отдельная забота).
- Чистота даёт: тестирование Model-части вызовом функции, time-travel /
  replay, воспроизводимость багов по логу Msg. Оговорка эталона: сам
  Cmd в Elm ОПАКОВЫЙ — несравним и неинспектируем, эффектную половину
  тестируют обходными паттернами; mate со сравнимыми
  эффектами-данными здесь СИЛЬНЕЕ эталона.

## 4. Managed effects — эффекты как ДАННЫЕ

- update НЕ выполняет эффекты — он их ОПИСЫВАЕТ: Cmd — иммутабельное
  значение-описание («сходи в сеть», «сгенерируй рандом»). Исполняет
  runtime, за пределами кода приложения.
- Если у эффекта есть результат — он приходит НОВЫМ Msg в тот же
  update; Cmd без результата (fire-and-forget: исходящий порт,
  pushUrl) легален. Никаких колбэков в обход цикла.
- `Cmd.batch [c1, c2]` — несколько команд из одного update; порядок
  ЗАВЕРШЕНИЯ не гарантирован (команды конкурентны), но каждая
  исполняется ровно столько раз, сколько описана — дубликаты легальны
  (два одинаковых Cmd = два исполнения).
- `Cmd.none` — явное «эффектов нет».
- init в полной форме: `init : flags -> (Model, Cmd Msg)` — стартовое
  состояние + стартовые эффекты (в Elm есть и sandbox-форма без Cmd,
  и application-форма с Url/Key — принцип один).
- Порты (ports) — JS-interop: единственная дверь наружу за пределами
  Cmd/Sub, и она тоже сообщение-ориентированная (исходящий порт = Cmd,
  входящий = Sub) — даже «грязный» внешний мир не ломает цикл.

## 5. Subscriptions — декларативные подписки

- `subscriptions : Model -> Sub Msg` — чистая функция: по ТЕКУЩЕЙ Model
  описывает, какие потоки внешних событий нужны (таймер, сокет,
  геолокация). Runtime сам сравнивает с предыдущим набором: новые
  включает, исчезнувшие гасит.
- Ключевое отличие от Cmd: Cmd — разовое действие, Sub — длящийся
  источник. И то и другое — данные; приложение никогда само не
  «подписывается» императивно.
- Следствие: активные подписки всегда выводимы из Model — нет
  «подвисших» подписок, чьё состояние живёт где-то ещё.
- В Elm НЕТ dispose/onDestroy: teardown длящегося выражается ТОЛЬКО
  исчезновением Sub из результата subscriptions. Для mate на Android с
  его lifecycle это главный конфликт с эталоном — runtime обязан взять
  teardown на себя.

## 6. Границы и следствия

- Runtime (в Elm — рантайм-система, поставляемая с компилятором)
  гарантирует: Msg обрабатываются ПОСЛЕДОВАТЕЛЬНО, по одному; update
  никогда не гоняется сам с собой; View видит консистентную Model.
- Весь недетерминизм (сеть, время, рандом) выдавлен на край — в
  runtime; ядро приложения детерминировано.
- Композиция: вложение троек Model/Update/View с маппингом Msg
  (Cmd.map/Html.map) — применяется точечно, на уровне страниц и крупных
  независимых блоков; канон Elm («The life of a file») предостерегает
  от иерархии мелких «компонентов» — масштабируют разбиением по данным
  и helper-функциям. Общей шины и глобальных сторов нет.

## 7. Чек-лист соответствия (для анализа mate)

1. Model — одна (в Elm — на приложение; у mate — на экран, осознанно),
   иммутабельная, всё поведение выводимо из неё.
2. update — чистый, тотальный, `(Model, Cmd)`.
3. Msg — факты, обрабатываются последовательно, единая точка входа.
4. Эффекты — данные; исполняет runtime; результат — новым Msg;
   дубликаты и порядок описания не теряются.
5. Подписки — декларативные, выводимы из Model.
6. init — `(Model, Cmd)`.
7. View — чистая проекция Model, все действия — через Msg.
