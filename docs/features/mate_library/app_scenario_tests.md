# Сценарные тесты приложения — киллер-фича библиотеки mate

Статус: концепт (2026-08-31, постановка юзера). Отдельная веха после
v0 — зависит от mailbox (О1) и MateObserver (О4), НЕ зависит от v1.

## Постановка (требования юзера)

Приложение = N экранов = N Mate-машин + навигация между ними через
handler'ы и общий класс навигации. Хотим:

- запускать ВСЕ Mate приложения вместе и прогонять их ПО СЦЕНАРИЮ
  с проверкой всех state'ов, эффектов и переходов;
- мокать только use case'ы эффект-хэндлеров — больше ничего;
- НИЧЕГО не писать дополнительно, кроме самих сценариев;
- по факту это проверка ПОЛНОГО функционала бизнес-логики приложения:
  все Mate вместе и есть бизнес-логика.

## Почему это возможно и дёшево (следствия уже принятых решений)

Фича не требует новых механизмов в ядре — она СОБИРАЕТСЯ из v0:

- **Mailbox (О1):** FIFO и однопоточный разбор → сценарий на
  TestDispatcher детерминирован на 100%: `send(msg)` +
  `advanceUntilIdle()` — и весь каскад (reduce → эффекты → outcome-Msg
  → reduce…) дошёл до конца. Без mailbox сценарные тесты гонялись бы
  с гонками.
- **MateObserver (О4):** харнес вешает RecordingObserver на каждый
  Mate — полная лента (Msg, state до/после, эффекты, каузальность,
  ошибки) каждого экрана. Это и материал для ассертов, и
  АВТОМАТИЧЕСКАЯ ТРАССА при падении сценария: «упало на шаге 7, вот
  дерево сообщений всех экранов до этого момента».
- **Роутинг семейств (О3):** харнес точно знает, какие эффекты —
  навигация (семейство NavigationEffect), и перехватывает их вместо
  исполнения.
- **Эффекты/Sub — сравнимые данные (П1):** ассерты на эффекты — прямое
  equals, без матчеров.
- **JVM, не девайс:** use case'ы замоканы → Room/Android не нужны;
  сценарий в `runTest` бежит миллисекунды. «Инструментальность» здесь —
  функциональная (весь функционал), а не платформенная.

## Дизайн

### AppHarness — тестовый мир приложения

Библиотечный класс (артефакт `mate-app-test`), который:

1. держит **реестр экранов**: `route → фабрика Mate` (+ параметры
   экрана, как nav-аргументы);
2. подменяет **Navigator** тестовым: NavigationEffect не дёргает
   NavController, а интерпретируется харнесом — стек route'ов, создание
   Mate целевого экрана (с параметрами из эффекта), закрытие текущего
   на Back. Граф навигации ЖИВОЙ: переходы происходят так же, как в
   приложении — теми же эффектами из тех же reducer'ов;
3. на каждый созданный Mate вешает RecordingObserver;
4. гоняет всё на TestDispatcher (`runTest`), время — виртуальное
   (`advanceTimeBy` для тиков/дебаунсов — счётчик «Удалить всё (5)»
   тестируется мгновенно).

### Сценарный DSL (единственное, что пишет автор теста)

```kotlin
@Test
fun `создание слова и переход в карточку`() = appScenario(registry) {
    stub<WordsTabUseCase> {
        onCreateWord returns 42L
        onTermsFlow returns flowOf(listOf(term("dom")))
    }

    launch(WordsTab)                          // стартовый экран
    send(Msg.OpenAddWordDialog())
    expectState<WordsTabState> { addWordDialogState.isOpen }

    send(Msg.UpdateWordInput("dom"))
    send(Msg.CreateWord("dom"))
    expectEffect(DatasourceEffect.CreateWord("dom"))   // equals, без матчеров

    send(Msg.OpenWordCard(42L))
    expectScreen(WordCard, args = 42L)        // навигация перехвачена
    expectState<WordCardState> { wordId == 42L }

    back()                                    // системный back в харнесе
    expectScreen(WordsTab)
}
```

Проверяемо ВСЁ, что есть в ленте observer'ов: state любого живого
экрана, эффекты (включая «эффект НЕ был послан»), последовательность
Msg, каузальность, текущий стек навигации.

### Стабы use case'ов

Use case'ы — уже интерфейсы (`deps/*UseCase` в каждом экране), других
швов не нужно: юзер прав, что «мокать больше ничего не надо». `stub` в
DSL — тонкая обёртка (mockk или рукописные фейки — решить в
реализации); дефолт харнеса: незастабленный вызов = громкий fail
(политика ошибок, та же философия громкости).

## Что приложение предоставляет ОДИН раз (не на тест!)

Честная цена «ничего не писать кроме сценариев» — одна декларация на
всё приложение, и она уже почти существует в DI:

1. **ScreenRegistry:** `route → { deps -> Mate(...) }` — формализация
   того, что сейчас разбросано по ViewModel-конструкторам и
   CompositionRoot. Фабрика принимает use case-интерфейсы (в проде —
   реальные, в харнесе — стабы).
2. **Маппинг nav-эффектов на route'ы** — сейчас живёт в
   `*NavigatorImpl` app-модуля строками кода; для харнеса он и
   переиспользуется: тестовый Navigator реализует те же интерфейсы
   Navigator'ов экранов.

Побочная польза: ScreenRegistry наводит порядок и в проде (сборка
экрана в одном месте вместо размазанной по DI).

## Ограничения (честно)

- Проверяется БИЗНЕС-ЛОГИКА, не UI: Compose-слой (что реально
  отрисовано) вне скоупа — это осознанно, для того есть превью и
  ручники.
- Derived-состояния UI-слоя (rememberX-хэндлы) не видны — только state
  Mate.
- Process death / SavedState — вне скоупа фичи.
- Экраны, ещё не переведённые на конвенцию (words до миграции), гоняются
  так же — харнесу конвенция атомов не нужна, только контракт Mate.

## Ценность

Полный функциональный прогон приложения — все экраны, переходы,
каскады эффектов — на JVM за миллисекунды, без эмулятора; сценарий
читается как ручник; упавший сценарий приносит полную трассу всех
экранов. Ручники остаются для UI и девайс-специфики, вся
бизнес-логика — под сценарной сеткой в CI.
