# Mate vs TEA — анализ соответствия

По фактическому коду `modules/core/mate` (2026-08-31, master 165a3c9).
Эталон — [elm_architecture.md](elm_architecture.md), нумерация пунктов —
из его чек-листа §7. Каждое отклонение описано ВМЕСТЕ со своим
решением — критика и варианты в одном месте.

## Состав модуля

`Mate` (раннер), `MateReducer` (+`ReducerResult = Pair<State,
Set<Effect>>`), `MateStateHolder`, `MateEffectHandler` /
`MateTypedEffectHandler` / `MateFlowHandler` /
`MateNavigationEffectHandler`, `NavigationEffect`+`Navigator`,
`ReducerChain` (begin/then/withEffect), `ReducerLogging`, `LogTags`,
`Constants`, test-хелперы (`mate/test`).

## Что соответствует TEA

- **(1) Model:** State — иммутабельный data-класс в `StateFlow`, один
  на экран; конвенция «explicit state flags» дожимает «всё поведение
  выводимо из Model».
- **(2) Update:** `reduce(state, message): Pair<State, Set<Effect>>` —
  прямой аналог `update : Msg -> Model -> (Model, Cmd)`. Тотальность —
  исчерпывающий `when` по sealed Msg; guard'ы = явные no-op.
- **(3) Msg как факты:** конвенция проекта уже elm-овская — плоские
  исходы (`MutationApplied/Rejected/Ignored`), маппинг outcome→Msg в
  handler'е ДО отправки; reduce доменные sealed'ы не разворачивает.
- **(4) Эффекты как данные:** Effect — data-классы; исполняют
  handler'ы через `coroutineScope.launch`; результат возвращается
  `consumer(::accept)` — новым Msg в тот же цикл. Колбэков в обход нет.
- **(6) init:** `Mate(initState, …, initEffects)` = `init : (Model,
  Cmd)`.
- **(7) View:** Compose читает StateFlow, шлёт Msg через `accept` —
  однонаправленно.

## Принцип mate поверх TEA

### П1. Различимые намерения: `Set<Effect>` — сознательный выбор

> **«У mate нет двух одинаковых причин его пить»** — для
> здравомыслящего человека.

Эффект — РАЗЛИЧИМОЕ намерение, не инструкция. Неразличимый дубль в
одном reduce не имеет семантики: если «нужно два одинаковых» — они на
самом деле различимы (цель, причина, порядковый номер), и эта
различимость ОБЯЗАНА жить в данных эффекта. `Set<Effect>` выражает это
структурой данных — умному подсказывает сам тип.

Это не отклонение от TEA, а собственный принцип поверх него, и он
опирается на два уважаемых основания:
- **«Make illegal states unrepresentable»** (мантра Elm-сообщества)
  в применении к эффектам: дубль без семантики не должен быть выразим;
- **idempotency keys распределённых систем:** кумулятивная команда без
  идентичности («инкремент», «отправь ещё раз») — плохой дизайн ещё до
  всякого Set: сеть и ретраи всё равно заставят добавить ключ.
  Различимость — в данные.

Обсуждено 2026-08-31 (заход с «Cmd.batch — список, дубли легальны»
разобран и отвергнут). Открытым остаётся один вопрос реализации v0:
опциональная debug-подсказка «для идиота» (громкий лог при фактическом
схлопывании дубля) — решить при выделении библиотеки.

## Отклонения и их решения

### О1. Нет гарантии последовательной обработки Msg — п.3

**Проблема.** `accept` не синхронизирован: `reduce` + `_state.value` —
Msg с двух потоков дают потерянную запись. Сегодня однопоточность
держится на конфигурации вызывающего (viewModelScope = Main.immediate:
UI, эффект-корутины и Flow-подписки сходятся на main, Room-suspend'ы
возвращаются в вызывающий контекст) — согласовано 2026-08-31: это
защита «сегодняшней конфигурации», НЕ контракт. Три дырки:
1. контракт scope'а не выражен ни типом, ни проверкой, ни KDoc;
2. `consumer` легально зовётся handler'ом с любого потока
   (`withContext(IO)`, `flowOn`) — компилятор и рантайм молчат;
3. даже на Main.immediate каскад Msg исполняется depth-first (стеком):
   эффект A от Msg1, синхронно пославший Msg2, исполнит reduce(Msg2) и
   ЕГО эффекты раньше эффекта B от Msg1. В Elm mailbox — строгий FIFO.

**Варианты решения:**
1. **Mailbox: `Channel<Msg>(UNLIMITED)` + единственный
   потребитель-цикл внутри раннера — РЕКОМЕНДУЕТСЯ.** `accept` =
   `trySend` (потокобезопасен по построению); цикл `for (msg in
   channel) { reduce → state → executeEffect }` даёт честный FIFO
   (каскадные Msg встают в хвост — семантика Elm); scope-агностичность,
   KMP-совместимость; API не меняется. Закрывает все три дырки. Цена:
   `accept` асинхронен — state обновляется «сразу после», а не «внутри»
   вызова (UI не отличает; тестам раннера — `runTest`/sync-режим в
   mate-test); при dispose закрыть channel.

   **Как устроен mailbox (термин — из актор-модели Erlang: очередь
   входящих + разбор строго по одному; Elm-runtime внутри устроен так
   же).** Цикл живёт В РАННЕРЕ Mate — не в reducer'е и не во ViewModel;
   reducer остаётся чистой функцией и не знает про очередь. Меняется
   ровно одно: КТО зовёт reducer.

   Сейчас — тот поток, что вызвал `accept` (и их может быть несколько
   одновременно):
   ```
   UI → vm.accept(msg) → mate.accept(msg):
                           ├─ reducer.reduce(state, msg)  ← на стеке вызова
                           ├─ _state.value = newState
                           └─ launch { эффекты }
   ```
   С mailbox — единственный внутренний цикл Mate (запускается один раз
   в init-блоке КЛАССА Mate, живёт в переданном scope):
   ```
   UI → vm.accept(msg) → mate.accept(msg):
                           └─ mailbox.trySend(msg)   ← положил и вышел

   for (msg in mailbox) {              ← вечный цикл-разборщик в Mate
       reducer.reduce(state, msg)      ← reducer зовётся ОТСЮДА
       _state.value = newState
       launch { эффекты }
   }
   ```

   **Использование во ViewModel почти не меняется:** конструктор тот
   же (цикл стартует в переданном viewModelScope и умирает с ним),
   `accept`/`state` — те же; на Main.immediate `trySend` будит
   разборщика немедленно — задержки кадра нет. Запрет в контракт: не
   читать `state.value` синхронно сразу после `accept` (таких мест в
   проекте нет — все чтения через подписку).

   **Уточнения по ревью (2026-08-31):**
   - **канал НЕ закрывать руками:** цикл умирает с отменой scope —
     этого достаточно; ручное закрытие создавало бы окно, где
     доживающие эффект-корутины теряют Msg молча. Неуспешный `trySend`
     (после отмены) — в error-лог/observer, не игнорировать результат.
     `dispose` остаётся для legacy-надобностей, к mailbox отношения не
     имеет;
   - **старт цикла — UNDISPATCHED**, initEffects прогоняются ПЕРВОЙ
     итерацией цикла (не отдельным executeEffect до него) — иначе на
     не-immediate диспатчере порядок init-эффектов и первых UI-Msg
     недетерминирован;
   - **порядок внутри итерации зафиксирован контрактом:** reduce →
     запись state → дифф подписок (О2) → запуск эффектов;
   - **код библиотеки не упоминает `Dispatchers.Main`** (KMP: на
     desktop/native его может не быть) — mailbox это и позволяет:
     FIFO не зависит от диспатчера; Main.immediate — рекомендация для
     UI-слоя в README, не зависимость;
   - исключения — см. сквозной раздел «Политика ошибок».
2. **Реентерабельный лок (`synchronized`)** — закрывает только дырку
   (2); FIFO не появляется, Mutex — самодедлок при реентере. Отвергнут.
3. **Main-only контракт + assert диспатчера** — дёшево, но остаётся
   стек vs FIFO и привязка к Android main. Полумера, отвергнута.
4. **CAS (`MutableStateFlow.update`)** — при retry эффекты reduce
   исполнились бы дважды: нарушение П1 и вообще дичь. Отвергнут.

### О2. Подписки императивные, не выводимы из Model — п.5

**Проблема.** Два механизма вместо `subscriptions(Model)`:
`MateFlowHandler.subscribe` включается при init НАВСЕГДА (гасится
только dispose); динамика — эффектами (`SubscribeSlice`,
`SetWindow(null)`, `ClearGroupWindows`) — включение/выключение
разбросано по веткам reducer'а, активный набор подписок нельзя увидеть
по State. Конвенция устоялась, но это самое концептуальное расхождение
с TEA.

**Решение (согласовано 2026-08-31): декларативные подписки, симметричные
эффектам.** Ключевая мысль: подписка — тот же эффект, только ДЛЯЩИЙСЯ;
оформляется зеркально О3. Требования юзера: изящно, декларация в одном
месте, очевидно и легко при использовании.

Три составляющие:

1. **Декларация — чистые данные + одна чистая функция** («одно место»):
   ```kotlin
   interface Sub                              // маркер, как Effect

   sealed interface GroupsSub : Sub {         // семейство экрана
       data class Slice(val dictionaryId: Long) : GroupsSub
       data class GroupWindow(val groupId: Long, val limit: Int) : GroupsSub
   }

   // ЕДИНСТВЕННОЕ место «что экран слушает и при каких условиях»:
   fun GroupsTabState.subscriptions(): Set<Sub> = buildSet {
       dictionaryId?.let { add(GroupsSub.Slice(it)) }
       expandedGroupWindows.forEach { (groupId, w) ->
           if (w.window > 0) add(GroupsSub.GroupWindow(groupId, w.limit))
       }
   }
   ```
   `expandedGroupWindows` groupstab — уже готовая декларация окон.

2. **Исполнение — семейства handler'ов, как О3:**
   ```kotlin
   interface MateSubscriptionHandler<Message, S : Sub> {
       val subFamily: KClass<S>
       fun flow(sub: S): Flow<Message>        // данные → поток Msg
   }
   ```
   Ветка `when` по подтипам семейства: `map` в Msg + `catch` на месте
   (политика ошибок — обязанность flow-фабрики, необработанное — в
   MateObserver О4). Это тело сегодняшних FlowHandler'ов БЕЗ
   flatMapLatest/merge-машинерии.

3. **Раннер диффит.** В mailbox-цикле (О1) после записи state:
   `subscriptions(newState)` против предыдущего набора ПО EQUALITY
   data-классов — новые `launch { flow(sub).collect { mailbox.send } }`,
   исчезнувшие cancel. Изменился параметр (`GroupWindow(5, 20)` ≠
   `GroupWindow(5, 10)`) → старая гаснет, новая стартует — сегодняшний
   `SetGroupWindow`, но автоматический.

**Как выглядит реализация в конкретном экране (две подписки):**
- `logic/Subs.kt` (новый, рядом с Message.kt): семейство `GroupsSub` +
  `GroupsTabState.subscriptions()` — см. п.1;
- `logic/GroupsSubHandler.kt`: класс из п.2 с `when` по двум подтипам;
- ViewModel: +2 параметра в конструктор Mate
  (`subscriptions = GroupsTabState::subscriptions`,
  `subscriptionHandlers = setOf(groupsSubHandler)`);
- УДАЛЯЕТСЯ: эффекты `SubscribeSlice`/`SetWindow`/`SetGroupWindow`/
  `ClearGroupWindows`, все `withEffect(Subscribe…)` в ветках reducer'а
  (DictionaryChanged просто пишет dictionaryId — дифф сам переключит
  slice; toggleGroup просто правит `expandedGroupWindows` — окно
  включится/погаснет само), `MateFlowHandler` и ручные
  subscribe/unsubscribe/dispose-пляски.
- Новая подписка = три касания: data-класс + условие в
  `subscriptions()` + ветка в handler'е.

**Почему изящно:**
- полная симметрия архитектуры: Effect — разовое намерение, Sub —
  длящееся; оба — данные, семейства, `Set`. П1 для подписок буквален:
  две одинаковых подписки бессмысленны (Sub в Elm — семантически
  множество);
- активные подписки выводимы из Model; «подвисшая подписка» невозможна
  по построению;
- тестируемость как у reducer'а: `assertEquals(setOf(Slice(1),
  GroupWindow(5, 10)), state.subscriptions())` — чистая функция; сегодня
  «какие подписки активны» нетестируемо без корутин.

Оговорки: пересчёт+дифф после каждого Msg (сеты маленькие — копейки);
кратенький gap при рестарте подписки между cancel и стартом — как и
сегодня у SetWindow. Этап v1, миграция экранов по одному.

**Уточнения по ревью (2026-08-31):**
- **устаревшие эмиссии:** cancel подписки не выгребает mailbox — Msg
  от погашенной подписки может примениться к новому state. Контрактная
  конвенция (мы по ней УЖЕ живём): Msg подписки несёт параметры своего
  Sub (`GroupWindowLoaded(groupId, …)`), reducer сверяет с текущим
  state и no-op'ит несовпадение;
- **«рестартни ту же подписку» невыразим по построению** (equal Sub не
  рестартует) — штатный приём: различающее поле
  (generation/номер попытки) в данных Sub — это ровно П1;
- **момент диффа** зафиксирован в порядке итерации О1 (state → дифф →
  эффекты); initial-дифф — от пустого набора на старте раннера;
- **контракт Sub: только данные** — лямбда или Flow-ссылка внутри Sub
  сломает equality-дифф (KDoc-требование);
- ошибки потока — см. «Политика ошибок».

### О3. Эффект прогоняется через ВСЕ handler'ы — п.4

**Проблема.** `runEffect` → `effectHandlerSet.forEach` — роутинга нет,
фильтр внутри каждого handler'а (`MateTypedEffectHandler.filter`).
Один эффект могут молча обработать два handler'а; «ни один не взял» —
тоже тихо.

**Решение (согласовано 2026-08-31): семейства эффектов + декларация
handler'а + громкие ошибки.** Владение развёрнуто обсуждением:
интерфейс принадлежит СЕМЕЙСТВУ ЭФФЕКТОВ (`GroupsEffect`,
`NavigationEffect` — уже так), а handler ДЕКЛАРИРУЕТ, какое семейство
исполняет — намерение не знает исполнителя, исполнитель заявляет права:

```kotlin
interface MateEffectHandler<Message, E : Effect> {
    val effectFamily: KClass<E>       // «я исполняю ЭТО семейство»
    suspend fun runEffect(effect: E, consumer: (Message) -> Unit)
}
```

Раннер строит реестр и роутит:
- **дубль** (два handler'а на семейство) — fail НА СОЗДАНИИ Mate;
- **сирота** (эффект, чьё семейство никем не заявлено) — громкий
  fail-fast ПРИ ДИСПАТЧЕ (`mateFail`: debug — краш, release —
  error-лог; политика — параметр раннера). Честно: это рантайм-, не
  compile-time-гарантия — Kotlin не выразит покрытие открытого
  множества семейств типами;
- резолв конкретный-класс→handler кэшируется (O(1) на горячем пути).

Правило контракта: **один handler на семейство, одно намерение — одно
исполнение** (в гармонии с П1); лог/метрики поверх — ДЕКОРАТОРОМ
handler'а, не вторым handler'ом в сете. `MateTypedEffectHandler` с его
тихим `filter` упраздняется. Миграция экранов механическая:
`filter`-каст → `override val effectFamily = GroupsEffect::class`. v0.

**Уточнения по ревью (2026-08-31, решения юзера):**
- **табличка подтверждена** против chain-of-responsibility («список,
  первый взявший»): chain дешевле сейчас, табличка строже навсегда —
  для публичной библиотеки выбрана строгость (принадлежность эффектов
  читается по заголовкам handler'ов, невалидная конфигурация не
  создаётся);
- **двойная принадлежность запрещена:** эффект — ровно в ОДНОМ
  семействе, вложенные семейства (family : family) запрещены; матч на
  два семейства при диспатче — громкий fail с именами обоих
  («раздели»). Легитимного юзкейса не нашлось: «кэш или сеть» —
  стратегия ВНУТРИ исполнителя (repository-паттерн, у раннера нет
  данных для такого выбора); «сделай и залогируй» — ДВА эффекта (П1);
  обёртка — декоратор. Правило: маршрутизация тупая по типу, вся
  умность — внутри исполнителя;
- **третий случай громкости:** дубль handler'ов — fail на создании,
  сирота — fail на диспатче, двойной матч — fail на диспатче;
- сирота в release (error-лог + drop) отличается от отвергнутого
  lifecycle-drop О5: это диагностика БАГА конфигурации, не потеря
  легитимного намерения; наблюдаемость — `onEffectOrphaned` в
  observer;
- честная оговорка: «декларация прав» — рантайм-типизация
  (гетерогенный реестр KClass, компилятор связь family↔runEffect не
  проверяет), KMP-совместимая (isInstance/equals KClass — common,
  рефлексия не нужна).

### О4. Логирование внутри reduce — п.2

**Проблема.** `ReducerLogging`/`logStep` — формально side effect в
чистой функции. Отклонение осознанное (наблюдаемость дороже пуризма,
лог идемпотентен и на результат не влияет), но библиотечно вредно
другим: тянет зависимость на проектный `:modules:core:logger`, а
`LogTags`/`Constants` — чисто проектные.

**Решение (согласовано 2026-08-31): `MateObserver` — наблюдатель
ПОЛНОГО цикла в раннере.** С mailbox (О1) весь цикл идёт через одну
точку — там и перехватываем:

```kotlin
interface MateObserver<State, Message, Effect> {
    fun onMessage(message: Message, stateBefore: State) {}
    fun onReduced(message: Message, before: State, after: State,
                  effects: Set<Effect>) {}
    fun onEffectStarted(effect: Effect) {}
    fun onEffectFinished(effect: Effect, durationMs: Long) {}
    fun onCausedMessage(parent: Effect, message: Message) {}
}
```

- `Mate(observers = emptyList())` — опционально, zero-cost без
  подписчиков.
- Покрывает ВСЁ изменение: Msg → state до/после (иммутабельные копии —
  хранение бесплатно) → эффекты reduce → старт/финиш/длительность
  исполнения; ключевое новое — КАУЗАЛЬНОСТЬ: `consumer` handler'а
  оборачивается раннером, Msg от эффекта регистрируется с родителем —
  по логу читается дерево «Msg1 → A→B → эффект X (34ms) → Msg2 → …».
  Чистый reduce + пары (before, msg) = задел time-travel/replay.
- В библиотеке — дефолтный `LoggingObserver(logger, tag, renderState,
  renderMessage)`: рендеры-лямбды решают, что печатать (полный state /
  счётчики / без PII). Интерфейс логгера — свой минимальный
  библиотечный.
- `ReducerLogging` (атомы, `logStep`) остаётся проектным сахаром
  ПОВЕРХ — прикладная детализация внутри reduce, библиотека о ней не
  знает; общий тег склеивает обе ленты grep'ом. `LogTags`/`Constants`
  из библиотеки убрать. v0.

**Уточнения по ревью (2026-08-31):**
- **+`onEffectFailed(effect, throwable)`** и
  **+`onSubscriptionError(sub, throwable)`** — без них падение эффекта
  обрывает каузальную ветку молча (и ссылка из О2 вела в никуда);
- **каждый вызов observer'а — в try/catch раннера:** кривой observer
  не имеет права убить mailbox-цикл (лог + продолжаем);
- **KMP:** длительность — `kotlin.time.Duration` через
  `TimeSource.Monotonic` (не `durationMs: Long` /
  `System.currentTimeMillis` — JVM-only, и monotonic семантически
  правильнее).

### О5. NavigationEffect исполняется без lifecycle-гейта

**Проблема.** Известный краш (Backlog «ВекторныйПиздеж»): `navigate()`
из корутины после ухода приложения в фон. TEA-принципу не противоречит
(Cmd есть Cmd), но runtime-обязанность «исполнять Cmd безопасно» не
выполнена.

**Решение (согласовано 2026-08-31): отложенная навигация в базовом
handler'е.** Единственный пункт, где у TEA нет готового ответа: в Elm
исполнитель Cmd (браузер) всегда жив, у нас исполнитель навигации
(NavController/активити) имеет lifecycle — «исполнять Cmd безопасно»
= «в STARTED».

`MateNavigationEffectHandler` получает абстрактный гейт готовности —
`StateFlow<Boolean>` (KMP-нейтрально; в Android кормится lifecycle:
STARTED = true):
- гейт открыт → исполнить сразу (как сейчас);
- закрыт → эффект в ОЧЕРЕДЬ (FIFO, дефолт);
- гейт открылся → исполнить накопленное синхронно подряд (NavController
  применяет пачку до следующего кадра — промежуточные экраны не
  мигают, но в back stack ложатся).

Отвергнутые варианты: drop-if-not-started (молча теряет намерение —
против П1); гейт в app-реализации Navigator'а (снова дисциплина
вызывающего, не контракт); буфер-1/replace КАК ДЕФОЛТ — разобран и
отвергнут обсуждением: двухшаговая навигация `navigate(A); navigate(B)`
обязана собрать back stack A→B, replace тихо портит семантику и
противоречит FIFO-линии О1 (порядок намерений свят). Replace остаётся
настраиваемой политикой для особых случаев.

Бонусы: фикс в одном базовом классе — все экраны получают бесплатно;
Backlog-краш PolyTrainer (navigate после ухода в фон) закрывается этим
же механизмом; отложенные/исполненные навигации наблюдаемы через
`MateObserver` (О4). Этап v1.

**Уточнения по ревью (2026-08-31, решения юзера):**
- **ВСЕ nav-эффекты всегда идут через очередь handler'а** — и при
  открытом гейте (очередь просто пуста, исполнение немедленное). Это
  закрывает критичную дырку: два nav-эффекта из ОДНОГО reduce летят
  конкурентными корутинами, и без сериализации обещание «A;B соберут
  back stack» держалось на удаче. Очередь = сериализация даром. Для
  прочих семейств порядок ЗАВЕРШЕНИЯ эффектов не гарантирован — как
  Cmd в Elm;
- **очередь БЕЗ лимита** (решение юзера): на практике 0–1 элемент,
  cap решал бы несуществующую проблему ценой потери намерений (П1);
  staleness-политика — опциональный параметр. Оговорки честно: после
  долгого фона исполнится вся накопленная пачка; очередь in-memory —
  умирает с процессом (как и весь Mate) — «закрытие Backlog-краша» не
  обещает переживание process death;
- **гонка «гейт открылся во время enqueue»** (check-then-act):
  гейт-очередь конфайнится в собственный однопоточный контур handler'а
  (мини-mailbox), плюс дренаж перечитывает гейт МЕЖДУ элементами —
  исполненный переход может сам захлопнуть гейт (Back);
- **порядок этапов исправлен:** миграция `MateNavigationEffectHandler`
  на effectFamily-контракт — в v0 (О3 упраздняет MateTypedEffectHandler,
  на котором тот построен); гейт-очередь — v1. Правило: nav-handler
  декларирует БАЗОВОЕ семейство `NavigationEffect::class` — иначе
  общий `NavigationEffect.Back` станет сиротой;
- **nav-handler — ОДИН на приложение, и это один SHARED-инстанс**
  (решение 2026-08-31): с navGraph-таблицей per-экранная логика
  handler'ов исчезает (нечего разворачивать — таблица знает сама), а
  навигация — глобальный ресурс (один стек), и гейт-очередь обязана
  быть одна, иначе очереди разных экранов не сериализованы между
  собой. App создаёт инстанс и суёт в сборку каждого Mate. Уточнение
  запрета вложенных семейств: интерфейсы-ПОДГРУППЫ внутри семейства
  (`WordsNavigationEffect : NavigationEffect`) легальны — запрещено
  лишь ДЕКЛАРИРОВАТЬ их как effectFamily; family здесь один — базовый;
- держатель collect'а гейта — сам nav-handler, у которого появляется
  опциональный lifecycle (attach(scope)/detach) в контракте библиотеки
  (после смерти MateFlowHandler это единственный длящийся handler).

## Политика ошибок (сквозная — по ревью 2026-08-31)

Ревью показало: у О1/О2/О4 одна общая незакрытая тема — исключения.
В Elm их нет вовсе (ошибки — значения); Kotlin-раннер обязан выбрать
поведение сам. Контракт:

1. **Mailbox-цикл не умирает никогда:** try/catch на итерацию —
   исключение из reduce/диффа/observer'а логируется (`mateFail`) и
   цикл продолжает. Иначе одно исключение молча замораживает экран:
   мёртвый цикл + вечно копящий UNLIMITED-канал, без краша.
2. **Эффекты:** исключение в handler-корутине → `onEffectFailed(effect,
   throwable)` в observer + политика `mateFail`. Каскад не обрывается
   молча.
3. **Подписки:** ошибка потока — прежде всего обязанность flow-фабрики
   (`catch` → Msg-fail, как сейчас); необработанное — `onSubscriptionError`
   + `mateFail`.
4. **Observer'ы:** каждый хук — в try/catch; сбойный observer — лог,
   цикл живёт.
5. **`mateFail` политика — параметр раннера** (debug: краш; release:
   error-лог) — в common нет BuildConfig, параметр — единственный
   KMP-валидный способ.
