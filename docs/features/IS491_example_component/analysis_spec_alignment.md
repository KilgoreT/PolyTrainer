# IS491 — аналитика: соответствие canonical-спеке компонентов

Дата: 2026-08-02. Метод: три независимых агента (домен/шаблоны · builtin/seed/миграции ·
экранный слой/данные) по брифу, спеке `docs/handbook/specs/component-constructor/spec.md`
и коду; затем синтез с дедупликацией и собственной верификацией ключевых утверждений
(сериализатор, квиз-фильтр, seed-механика — проверены чтением кода, не со слов агентов).

Вердикт одной строкой: **доменно фича ложится чисто, но два утверждения брифа
опровергнуты кодом (миграция всё-таки нужна; «как IMAGE» не защищает от квизов), а
главная скрытая работа — одно-строковый edit-пайплайн карточки и одно-полевой
сериализатор.**

---

## 1. Противоречия (бриф или спека vs код)

### П1. «Миграция БД не требуется» — неверно: нужен data-backfill + bump версии Room
Бриф прав только про DDL: колонки не меняются, CHECK-констрейнтов на `template_key`
нет, TypeConverter'а на template нет (`Database.kt`, версия 12). Но seed builtin живёт
в транзакции создания словаря (`CoreDbApiImpl.kt:147`, `seedBuiltInsForDictionary`) —
**существующие словари юзеров builtin «Пример» не получат никогда**. Прецедент решён
ровно так, как надо повторить: `part_of_speech` доставлен в существующие словари шагом
миграции (`Migration_011_to_012.kt:76,245` — `seedPartOfSpeechPerDictionary`,
`INSERT … SELECT FROM dictionaries`). Итого для IS491: bump 12→13, `Migration_012_to_013`
только с data-INSERT (без DDL), schema-json 13 идентичен 12; плюс `EXAMPLE` в
`seedBuiltInsForDictionary` для новых словарей; `position = 2` (после части речи;
UNIQUE на position нет, коллизии нет).

### П2. «В квизах не участвует, как IMAGE» — фильтр пикера этого не обеспечивает
Фактический фильтр — чёрный список: `.filter { it.template != ComponentTemplate.CHOICE }`
(`app/.../quizchat/QuizChatUseCaseImpl.kt:139`). `captioned_text` — не CHOICE →
и builtin «Пример», и кастомные компоненты шаблона **просочатся в пикер квизов**,
вопреки Д6. Аналогия «как IMAGE» обманчива: IMAGE не всплывает только потому, что
IMAGE-компоненты нельзя создать; captioned-компоненты юзер создавать сможет.
Фикс — заменить чёрный список белым (`it.template == ComponentTemplate.TEXT`):
закрывает Д6, IMAGE и все будущие шаблоны по умолчанию.

### П3. «Envelope проектировался под несколько полей» — верно для формата, неверно для кода
Формат `{"fields":{"<fieldName>":{...}}}` действительно multi-field-ready
(doc `TemplateValuesJson.kt:14`, там же обещание «composite values добавляются без
breaking changes»). Но и запись, и чтение захардкожены под единственный ключ
`"value"`: `toJson()` кладёт только его, `parseTemplateValues()` читает
`fields.getJSONObject("value")` **до** ветвления по шаблону
(`TemplateValuesJson.kt:31-69`). `ComponentTemplate.fields` (§5) ничем в data-слое
не управляет — декоративен. Captioned-ветка сериализатора/парсера — обязательная
новая работа, а не «формат уже готов».

### П4. Спека канонизирует «Пример → Перевод» — реальный builtin будет «Пример → Лексема»
§1, §3, §5 спеки многократно используют «Пример → Перевод» как эталонную иллюстрацию
зависимости компонент-от-компонента и мульти. Решение Д2 — `dependsOn = Lexeme`
(вариант `Component(translation)` отклонён: ломается в словарях с выключенным
переводом). После IS491 canonical-спека будет учить неправде о реальном builtin.
Нужна правка примеров §1/§3/§5 (либо оговорка «„Пример → Перевод“ — иллюстрация
кастомной привязки; builtin „Пример“ зависит от лексемы»).

### П5. Спека §18 описывает мёртвый рендер-путь карточки
§17–§18 ведут через `ComponentByTemplate → ComponentBlock → TextWidget`, но карточка
фактически рендерит значения через `LexemeComponentsBlock → ComponentValueField →
LexemeEditableText`; `ComponentByTemplate`/`TextWidget` вызываются только из
`ui/unused/CheckedTextWidget.kt` — мёртвый код. Планировщик IS491, доверившийся
спеке, промахнётся модулем: двухполевой виджет встраивается **в `ComponentValueField`**
(третья ветка рядом с ранним return CHOICE-чипа). Спеку поправить; судьбу мёртвых
виджетов решить (снести или пометить).

## 2. Обязательный скоуп IS491, который бриф не называет

### С1. Одно-строковый edit-пайплайн карточки → нужна пара (text, caption?)
Строковость сквозная: `ComponentValueState.origin/edited: String` (`State.kt:94-95`),
`Msg.UpdateComponentValueInput(value: String)`, `CommitOutcome.Update(text: String)`,
`textValuesOf()`, `commitDecision()` сравнивает две строки, commit-хелперы строят
`textValuesOf(outcome.text)`. Captioned требует пары на каждом узле. Решение — сделать
узлы template-aware (носить `TemplateValues`, а не `String`), а не плодить вторую
параллельную пару строковых полей.

### С2. Ловушка «origin lossy» бьёт по фиче напрямую — фикс обязателен
`toComponentValueState()` пишет `origin = data.asText().orEmpty()`, а `asText()`
non-null только для `TextValues` → у `CaptionedTextValues` origin будет `""` →
пустой коммит уронит значение в `LocalRemove` вместо `PessimisticRemove` — значение
исчезает из UI, оставаясь в БД. Это дословно существующий backlog-пункт
«IS481 wordcard_components: origin lossy» — до сих пор он был теоретическим
(не-текст недостижим), IS491 делает его реальной потерей данных builtin «Пример».
Закрывается тем же template-aware рефактором из С1 — вместе с backlog-пунктом.

### С3. Валидация Д7 не выражается текущим commitDecision
Сейчас «пусто» = `edited.trim().isEmpty()` по единственной строке. Для captioned
«пусто» определяется **только полем text** (caption не считается); draft-anchor
(`commitDraftLexeme`) должен якориться на text. Инвариант §7.4 «пустых значений не
существует» обеспечивается только UI-гейтом — data-guard'а нет; для IS491 достаточно
UI-гейта (как у TEXT), но владельца валидации стоит зафиксировать в спеке явно.

### С4. Fail-soft парсинга: all-or-nothing неверен для опционального поля
`parseTemplateValues` на любой `JSONException` возвращает null → skip всего значения.
Для captioned битый/неизвестный caption уронит и text. В новой ветке — defensive:
text обязателен (битый text → null, как сейчас), битый caption → значение живёт с
caption = null + лог. Представление отсутствующего caption в envelope — **опущенный
ключ** (не пустая строка); зафиксировать в спеке §10.

### С5. Display-слой: три сайта покажут сырой ключ + exhaustive-when
`componentDisplayName` (BuiltInDisplay.kt) → покажет `"example"`, `labelOfRef` →
`"EXAMPLE"`, `componentLabelOf` — спец-ветка только для PART_OF_SPEECH. Нужен ресурс
(рус. «Пример» / англ. "Example") и ветки во всех трёх. Прочие exhaustive-when по
`ComponentTemplate`/`BuiltInComponent` (labelRes, toJson/parse, ComponentChoiceItem
и др.) компилятор перечислит сам — это защита, а не риск.

### С6. Данные: запрос исполним, дедуп — только в Kotlin
JSON1 в bundled SQLite подтверждён тестами (`json_extract` доступен) → distinct +
частотность: `SELECT json_extract(value,'$.fields.caption.value') AS cap, COUNT(*)
… WHERE component_type_id=:typeId AND removed_at IS NULL GROUP BY cap ORDER BY
COUNT(*) DESC`. Скоуп запроса — строго `component_type_id` (пословарность выходит
автоматически). Подсказки — one-shot запрос при открытии поля, не Flow (combobox
живёт секунды, подписка — лишние гонки).

**UPD 2026-08-02 (ревью):** решение Д4 изменено — **регистр значим, дедупа нет**
(`ielts`/`IELTS` — отдельные пункты). Прежний вывод «`COLLATE NOCASE` не годится
для кириллицы → Kotlin-дедуп» стал неактуален: дедуп не нужен вовсе, достаточно
точного `GROUP BY`; tie-break при равных частотах — алфавит.

### С7. Combobox строить с нуля
Готового «ввод = новое значение + фильтр списка» в проекте нет (только кастомные
DropdownMenu и OptionPickerDialog). База — M3 `ExposedDropdownMenuBox` либо кастом
`TextField` + `DropdownMenu` в стиле существующих виджетов.

## 3. Подтверждения консистентности (проверено, конфликтов нет)

- **Инвариант §7.8** (последнее включённое ядро): «Пример» не ядро — не затрагивает.
- **Участие §6 + multiple**: `Lexeme` + `core=false` → показывается у оформленной
  лексемы, как часть речи; запрет мульти привязан только к CHOICE — captioned
  проходит. Multiple у builtin — новый прецедент, структурного запрета нет.
- **«Пример» как цель зависимостей** (§4): мульти-цель деактивируется при удалении
  последнего значения — путь уже реализован, спец-логики не нужно.
- **Template picker конструктора**: radio-группа итерирует `ComponentTemplate.entries`,
  дизейблит только IMAGE — новый шаблон становится выбираемым автоматически;
  single/multiple-чекбокс generic (Д1 работает без изменений).
- **Многострочный ввод**: `LexemeTextFieldWidget` уже `singleLine = false` — поле
  text даром; caption'у нужен singleLine-вариант.
- **Forward-compat**: старая версия над `captioned_text` — тихий skip типа и его
  значений (fail-soft, строки в БД живы). Для single-user downgrade-сценария риск
  низкий; для бэкапов — прямой вопрос к замороженному IS488 (учесть при разморозке).
- **Backlog-запись** «seed не выполняется на destructive-fallback» (ВекторныйПиздеж)
  **устарела**: seed давно перенесён из `onCreate` в `addDictionary` — после
  destructive словарей ноль, сеять нечего. Запись стоит актуализировать (лживый
  комментарий в `RoomModule` — отдельный мелкий долг).

## 4. Критический разбор предложений агентов (моя позиция)

**Отклонено: generic-сериализатор, управляемый `ComponentTemplate.fields` +
`Field.required`.** Агент домена предложил сделать envelope-движок декларативным
(итерация по fields, обязательность из флага) — «чтобы модель не врала».
Возражение: для двух-трёх шаблонов с фиксированным составом полей это обмен
compile-time-гарантий (exhaustive when по sealed `TemplateValues`) на рантайм-схему,
ошибки которой всплывут только на девайсе. Опциональность caption выражается типом
(`caption: Primitive.Text?`) — сильнее, чем флаг `required` в рантайм-модели.
Правильный фикс «декоративности» `fields` — честная третья when-ветка сейчас; если
шаблонов станет 5+, вернуться к идее. `Field.required` не вводить.

**Принято в Backlog (📦): seed-реконсиляция builtin при открытии БД.** Идемпотентный
`INSERT … WHERE NOT EXISTS (ключ, словарь)` по всем словарям в `onOpen` — тогда
каждый будущий builtin доезжает в существующие словари **без** миграции на каждый
случай, заодно закрывается устаревший destructive-fallback-пункт и лживый комментарий
RoomModule. В скоуп IS491 не входит (меняет точку seed — отдельный бриф); для IS491 —
классический backfill 12→13 по образцу part_of_speech (П1).

**Принято: one-shot подсказки** (не Flow) — combobox короткоживущий, реактивность
не даёт ценности, подписки добавляют гонки.

## 5. Итоговые рекомендации

В скоуп IS491 (сверх брифа, обязательное):
1. Миграция 12→13: data-backfill «Пример» во все словари + `EXAMPLE` в seed (П1).
2. Белый список шаблонов в квиз-пикере (П2).
3. Ветка `CaptionedTextValues` в сериализаторе/парсере с defensive-caption (П3, С4).
4. Template-aware edit-пайплайн карточки — закрывает С1 + С2 (и backlog «origin
   lossy») + С3 одним рефактором.
5. Display-ресурсы и три сайта (С5); combobox-виджет (С7); частотный
   distinct-запрос (С6, регистр значим — UPD).

Правки брифа (2 формулировки): «миграция схемы не требуется» → «DDL не нужен;
нужен bump 12→13 + data-backfill»; «как IMAGE» → «белый список шаблонов в пикере».

Правки спеки (после реализации, вместе с фичей): примеры «Пример → Перевод»
(П4), рендер-путь §18 (П5), владелец валидации пустого значения (С3), формат
multi-field envelope и опущенный ключ caption (С4).

Backlog: добавлен пункт «seed-реконсиляция builtin в onOpen» (ВекторныйПиздеж);
пункт «origin lossy» закрывается скоупом IS491; пункт «seed на destructive-fallback»
помечен к актуализации (устарел).
