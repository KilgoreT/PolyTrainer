# IS493 — Анализ: публикация групп и импорт (решения П1–П3)

Статус: **семантика зафиксирована на уровне, достаточном для архитектуры v1**
(П1–П3 решены 2026-08-04); детали фичи публикации — сильно позже (П4–П6
отложены). Вводная: группы будут публиковаться — другие пользователи видят их,
добавляют себе и учат слова. Задача этого документа — чтобы архитектура v1 была
построена с учётом этого факта.

---

## 1. Принятая семантика импорта (П1–П3)

- **П1. Импорт — всегда в ТЕКУЩИЙ словарь.** Каталог расшаренных групп виден
  только изнутри словаря и фильтруется по языку этого словаря. Сценария «импорт
  в новый словарь» не существует; язык — не коллизия, а ключ витрины (пакет
  несёт язык словаря-источника).
- **П2. Совпадение текста слова (trim + case-insensitive) — сигнал для ревью,
  НЕ идентичность.** Перед импортом — один preview-экран: сводка + список
  совпавших слов (мои значения vs значения группы), per-word чекбокс
  включить/исключить (по умолчанию включено). Отказ = слова из пакета нет
  нигде (ни строки, ни membership); мой контент не трогается. Никаких
  «выключенных» слов и никаких цепочек модалок.
- **П3. Импортированное слово — ВСЕГДА новая строка `words`** (дубликаты текста
  в словаре легальны), с лексемами и значениями из пакета. Слово живёт и в
  общем списке, и в импортированной группе. Никакого reuse/склейки моих строк —
  даже при побайтовом совпадении значений. Дубли в квизах и списке слов —
  осознанно принятая цена.

### Почему дубль-модель, а не склейка (обоснование П3)

- Импортированная группа = **точная копия авторского контента**; мои и
  авторские лексемы не смешиваются в одном слове — всегда ясно, что чьё.
- Повторный импорт / будущее обновление версии: поддерево **владеет** своими
  словами → provenance вешается на импортированные строки целиком, без
  распутывания «какие лексемы в моём слове чужие».
- Прогресс (живёт на лексеме) при склейке всё равно не переносился бы —
  авторская лексема для подписчика новая в любом случае.
- Matching перестаёт влиять на корректность: он нужен только для ревью-экрана.
  Канонизация value-JSON для сравнения лексем НЕ требуется (сравнение смыслов
  ушло из механизма — на ревью значения показываются глазами).

Известные цены: двойные карточки в квизе при совпадающем контенте; одинаковые
строки в списке «Слова», неразличимые, пока список не показывает группы
(усиливает мотивацию бейджей групп в списке слов — вне скоупа v1).

## 2. Механизм импорта (следствие П1–П3)

Импорт = **чисто аддитивная вставка**, ни одна существующая строка подписчика
не изменяется и не удаляется:

1. поддерево групп пакета → новые строки `dictionary_groups` (корень поддерева
   — в корень словаря);
2. слова пакета (минус исключённые на ревью) → новые строки `words` + их
   лексемы + значения;
3. membership пакета → новые строки `word_groups` (только на импортированные
   слова);
4. схема компонентов: builtin — маппинг по `system_key` на seed-строки словаря;
   user-defined и прочее — отложено (П6).

Пласт user-state (прогресс, статистика) не импортируется никогда.

## 3. Отложено до фичи публикации (П4–П6)

Решения не нужны для v1 — модель не блокирует ни один вариант:

- **П4.** Коллизия имени импортируемой группы с моей (sibling-unique):
  автосуффикс vs диалог. Разрешимо программным rename — уникальность имён
  остаётся UseCase-валидацией, не БД-констрейнтом (уже так).
- **П5.** Судьба `quiz_configs` в пакете (курация автора vs предпочтение
  подписчика).
- **П6.** User-defined типы компонентов при импорте (всегда новые vs match).
  Плюс: формат пакета, версия схемы, provenance (`origin_publication_id` —
  аддитивная миграция), сервер/каталог/аккаунты, коллизия имени группы с
  лейблом «Не разобрано» из другой локали (import-валидация).

## 4. Итог: что v1 ОБЯЗАН обеспечить (дельта к §6.3 архитектуры)

Схему v1 принятые решения НЕ меняют. Обязательства — запреты и инварианты:

1. **Не вводить уникальность текста слова** в словаре (ни UNIQUE, ни
   UI-валидацию «такое слово уже есть» как блокер) и **не завязывать логику на
   текст слова как идентичность** — дубль-модель П3 требует легальности дублей.
2. **Уникальность имён групп среди сиблингов — только UseCase**, не
   БД-констрейнт (импорту нужен программный авторезолв). Уже решение А3.
3. **Самодостаточность словаря**: группы и значения не ссылаются ни на что вне
   словаря; инвариант «values — только на пословарные типы» (global-охват
   компонентов сломал бы пакет).
4. **Идентичность builtin — только `system_key`** (на нём держится маппинг
   схемы при импорте). Уже инвариант IS486.
5. **Никакой семантики на локальных id**; «Не разобрано» — не строка БД.
   Порядок сиблингов — алфавитный (В7: поля `position` в схеме нет; пакет
   порядок не несёт). Уже в §6.3.
6. **Язык словаря (`numericCode`) — ключ витрины каталога**; в v1 ничего не
   делать, но не терять поле при будущих правках словаря.
7. **Прогресс строго в пласте user-state** (отдельные таблицы) — не подмешивать
   учебное состояние в words/lexemes/groups.
8. UUID/provenance/published-флаги в v1 **не вводить** — дубль-модель закрывает
   все сценарии аддитивной миграцией при фиче публикации (подтверждено ревью).

Требование «канонизация value-JSON для матчинга лексем» из ранней версии
анализа **снято** — П3 убрал сравнение лексем из механизма импорта.
