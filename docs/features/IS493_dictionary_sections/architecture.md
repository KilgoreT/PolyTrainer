## 1. Смысловая модель: три пласта данных

Классификация — на уровне **колонок**, не таблиц (audit-колонки живут в
таблицах пластов 1–2, но принадлежат пласту 3; экспорт фильтрует поля):

| Пласт | Что это | Примеры | Публикуется? |
|---|---|---|---|
| **Структура** | Как контент организован | `dictionary_groups`, `word_groups` | да |
| **Контент** | Что учим | `words`, `lexemes`, `component_values`, схема компонентов словаря | да |
| **Пользовательское состояние** | Как идёт учёба | quiz-прогресс, статистика, audit-даты | **никогда** |

Группа — пласт «структура»: не владеет контентом, а **выделяет срез словаря**.
`quiz_configs` — классификация отложена до фичи публикации (П5).

## 2. Доменная модель

### 2.1 Сущности

- **Group** — узел: `id`, `dictionaryId`, `parentGroupId?` (null = корень),
  `name`, audit. Поля `position` НЕТ (В7): порядок сиблингов — алфавитный,
  **locale-aware компаратор в Kotlin** (не SQLite NOCASE — кириллица).
  Rename может менять позицию узла в списке — скролл-скачок принят как цена
  В7 (expand-state устойчив: ключ — id).
- **GroupTree** — агрегат: всё дерево групп словаря. Граница — словарь
  (инварианты проверяемы только на полном дереве). Грузится целиком (десятки
  узлов), собирается в памяти. **Fail-soft:** узел с битым `parent_group_id`
  пропускается с поддеревом (прецедент — skip-row маппер `ComponentTypeDb`).
- **Membership** — «слово W привязано к узлу G». Привязка к конкретному узлу;
  членство в предках — производное.
- **«Все»** (концепт-правки 2026-08-06, заменила «Не разобрано») — НЕ строка
  БД. В domain — маркер-узел без имени; строку подставляет UI из ресурсов.
  Единственная виртуальная группа: первая на корне вкладки, содержит ВСЕ слова
  словаря, счётчик = их число (Р6). Kebab/действий нет.
- **Инвариант «папка или лист» (2026-08-06):** группа либо содержит подгруппы
  (папка — слова добавлять нельзя), либо слова (лист — подгруппы создавать
  нельзя). Пустая группа — тип по первому действию; проверка по живому
  содержимому в транзакции. Смешанных узлов и внутренних маркеров не
  существует. Лист показывает слова напрямую (В2). Механизм конвертации —
  будущая фича.

### 2.2 DisplayNode (ADT зафиксирован)

```
sealed DisplayNode
  Group(id, name, children: List<DisplayNode.Group>,
        directWords: List<WordId>, subtreeWordCount: Int)
  AllWords(words: List<WordId>, count: Int)   // «Все»; имя — в UI
```

Правила сборки `GroupTree + membershipSlice → DisplayTree` (чистая функция в
domain, компаратор — параметром): у Group с children и directWords прямые
узлы «папка XOR лист» (аномальный смешанный — fail-soft как папка); у листа directWords
рендерятся напрямую (В2); корень дерева — синтетический уровень со списком
AllWords(все слова словаря) первым + корневые Group.
`subtreeWordCount` = distinct слов поддерева (В3).

**Контент слов — лениво (Р4):** DisplayTree несёт только `WordId` +
счётчики; тексты/лексемы слов подгружаются при раскрытии узла отдельным
запросом (вкладка «Слова» не зря пагинируется — словарь бывает на тысячи
слов, весь контент в память не тянем). Структура и счётчики — из лёгкого
id-среза.

### 2.3 Инварианты

1. `parent.dictionaryId == child.dictionaryId`.
2. Ацикличность — `createsCycle` (паттерн IS486). В v1 недостижима ни одной
   операцией (reparent вне скоупа) — guard-задел, обязательного вызова нет.
3. Имя: **normalize = trim + NFC + case-insensitive сравнение
   (locale-aware lowercase)**; хранится как введено. Непустое, уникально среди
   **живых** сиблингов, резерв «Все» — по **всем локализациям**
   ресурса. Множество зарезервированных строк **инжектится в валидатор
   параметром** (Р7): его перечисляет UI-слой из ресурсов всех локалей проекта
   (ru + default), domain остаётся zero-deps — тот же приём, что компаратор.
   UNIQUE-индекс в БД не вешаем (NULL parent + soft-delete) — UseCase-валидация,
   паттерн M13. Та же normalize-функция — для импорта публикации.
4. `word_groups`: слово и группа из одного словаря; группа живая на момент
   вставки; PK `(word_id, group_id)`.

### 2.4 Транзакционная граница (Р1)

Каждая мутация агрегата — «чтение актуального состояния → валидация →
запись» — выполняется **целиком внутри `CoreDbApiImpl`** одной транзакцией
`database.useWriterConnection { immediateTransaction { } }` (фактический API
проекта; immediate берёт write-lock с начала — deferred не защищает: два
конкурента прошли бы валидацию на своих снапшотах). Для этого `core-db-impl`
получает зависимость на `modules/domain/group` и зовёт его чистые валидаторы
изнутри транзакции. Use case-слой — **тонкая делегация** в `CoreDbApi`,
валидаций не содержит. Тестами конкурентность не гоняем — покрывается
последовательный путь (DAO-тесты проекта однопоточные), что зафиксировано
как осознанное ограничение.

### 2.5 Операции

Мутации (все — в транзакции §2.4):

- `createGroup(dictionaryId, parentId?, name) → CreateGroupOutcome` — Success |
  EmptyName | DuplicateSibling | ReservedName | ParentNotFound |
  **ParentHasWords** (синхрон с А18, ревью Э3 A-C: у родителя есть прямые
  слова — подгруппу создавать нельзя; ветка-задел с Э3, срабатывает с Э6).
  **ParentNotFound = отсутствует ∪ soft-deleted ∪ чужой словарь.**
- `renameGroup(id, name) → RenameGroupOutcome` — ошибки имени + NotFound.
  **NotFound (rename/delete) = отсутствует ∪ soft-deleted** (распространение
  А17, ревью Э3 D-5). Rename исключает self из сиблингов (смена регистра
  собственного имени легальна, ревью D-1/T-1).
- `deleteGroup(id) → DeleteGroupOutcome` — Success | NotFound. Поддерево
  пересчитывается по БД внутри транзакции: soft-delete узлов + hard-delete их
  строк `word_groups`.
- **[Э6-синк 2026-08-28]** `deleteGroupWithWords(groupId, chunkSize=999)
  → DeleteGroupWithWordsOutcome` — ДЕСТРУКТИВ: одна транзакция:
  liveness → ids → samples-легаси (без FK) → hard-delete слов чанками
  (FK CASCADE: lexemes/component_values/write_quiz/word_groups всех
  групп) → soft-delete группы. Success(deletedWords) — факт на момент
  транзакции; NotFound — слова не тронуты.
- **[Э5-синк 2026-08-23, ревью Arch-4]** membership — ПАРА методов вместо
  `setMembership` (идемпотентные исходы на направление, симметрия
  Create/Rename/Delete-outcomes):
  `addWordToGroup(wordId, groupId) → AddMembershipOutcome` — Added |
  AlreadyIn (дубль гасится составным PK, OR IGNORE→rowid) | GroupNotFound
  (мертва ∪ чужой словарь — JOIN-check) | WordNotFound (hard-delete);
  `removeWordFromGroup(wordId, groupId) → RemoveMembershipOutcome` —
  Removed | NotFound (идемпотентный успех). Порядок проверок: слово →
  группа-в-словаре-слова → insert, всё в одной immediateTransaction,
  открытой до первого чтения.

Чтение (Flow):

- `groupTree(dictionaryId)` — живые группы словаря.
- `membershipSlice(dictionaryId)` — id-срез: пары (wordId, groupId) по живым
  группам + id слов словаря вне групп. **Наблюдает ТРИ таблицы** (Р5): `words`,
  `dictionary_groups`, `word_groups` — новое слово обязано переэмитить
  «Все» и счётчики (прецедент бага — stale-опции IS486). Один `@Query` с
  LEFT JOIN от `words` наблюдает все три автоматически.
- `wordsContent(ids)` — контент слов раскрытого узла (Р4, ленивая догрузка).
- `wordGroups(wordId)` — живые группы слова (шапка карточки).
- `deleteImpact(id) → GroupDeletionImpact` — N подгрупп + M слов. M =
  `COUNT(DISTINCT word_id)` по поддереву, исключая слова с членствами вне
  поддерева, где **внешние членства фильтруются по живым группам** (Р9а —
  иначе зомби-членство даёт недосчёт). DAO-SQL запрос (Р9в), поддерево — bind-
  списком id; лимит SQLite 999 переменных покрыт допущением «десятки узлов»
  (Р9б — явная граница; импорт публикации обязан её перепроверить).
  **TOCTOU принят** (Р9г): числа конфирма могут устареть к моменту удаления —
  фактическое удаление всегда пересчитывает поддерево по БД, конфирм —
  ориентир, не контракт.

Все read'ы по `word_groups` JOIN'ят на живые группы.

Задел на тренировку (Д9, вне v1): `resolveSubtreeWordIds(groupId)`.

## 3. Данные

### 3.1 Таблицы

```
dictionary_groups
  id                PK autoincrement
  dictionary_id     FK → dictionaries.id  ON DELETE CASCADE, NOT NULL, INDEX
  parent_group_id   FK → dictionary_groups.id  ON DELETE CASCADE, NULL, INDEX
  name              TEXT NOT NULL
  created_at / updated_at              NOT NULL
  removed_at        NULL               -- soft-delete, образец: ComponentTypeDb (M13)

word_groups
  word_id           FK → words.id             ON DELETE CASCADE, NOT NULL
  group_id          FK → dictionary_groups.id ON DELETE CASCADE, NOT NULL, INDEX
  created_at        NOT NULL
  PRIMARY KEY (word_id, group_id)     -- составной; INDEX(group_id) обязателен
                                       -- (PK покрывает только префикс word_id)
```

Образец стиля entity — `ComponentTypeDb` (M13). Self-FK CASCADE по дереву —
прецедент `depends_on_type_id`, работает на bundled SQLite.

### 3.2 Семантика удаления

Soft-delete — пользовательский путь, FK CASCADE — страховка hard-пути:

- Удаление группы: одна транзакция — поддерево запросом по БД → soft-delete
  узлов → hard-delete их строк `word_groups`. `removed_at` — audit, не undo.
- FK CASCADE — hard-путь: удаление словаря; hard-delete слова (Д5).
- Read'ы групп — `removed_at IS NULL`; `word_groups` — JOIN на живые.
- Накопление soft-deleted строк — принято (низкая кардинальность, YAGNI).

### 3.3 Миграция 12→13

Только DDL (data-backfill нет). По прецеденту IS481: CREATE TABLE буквально
совпадает с экспортом `13.json` — **внимание** (Р12): составной PK — новая
форма DDL для проекта (в референс-миграции только autoincrement id), выверять
против 13.json руками; `CREATE TABLE/INDEX IF NOT EXISTS` (defensive, как в
`Migration_011_to_012`); имена индексов по конвенции Room
`index_<table>_<col>`. Idempotency-тест для чистых CREATE — не обязателен.

## 4. Модули и слои

### 4.1 Три модуля вместо одного (Р2)

Нижний таб словаря расщепляется: `dictionaryTab` (1 модуль) → **3 модуля**.
Заодно чинится нейминг-рассинхрон `Vocabulary*`/`DictionaryTab*`:

```
modules/screen/vocabulary     NEW  host: Scaffold, TabRow, selectedTab,
                                   контекстный FAB, текущий словарь, snackbar
modules/screen/wordstab       MOD← контент вкладки «Слова» (перенос из
                                   dictionaryTab максимально как есть:
                                   WordListWidget и начинка не трогаются,
                                   режется только Scaffold-обвязка)
modules/screen/groupstab       NEW  контент вкладки «Группы»: аккордеон, диалоги
modules/domain/group          NEW  чистый Kotlin, zero deps: Group, GroupTree,
                                   DisplayTree, Outcomes, валидации
modules/widget/grouptree      NEW  layout-скелет дерева со слотами строки;
                                   потребители: groupstab и wordcard-пикер
core/core-db-api              MOD  api-entities + методы CoreDbApi
core/core-db-impl             MOD  entities, DAO, миграция; зависимость на
                                   domain/group (валидация в транзакции, §2.4)
modules/screen/wordcard       MOD  группы в шапке + пикер
```

**Контракт вкладки** (host ↔ вкладка, через CompositionRoot в app — screen-
модули друг о друге не знают): content-слот + FAB-действие вкладки.

- Host владеет: Scaffold, TabRow (в верхе content, НЕ в topBar-слоте), явный
  `selectedTab`, FAB (диспетчеризует действие активной вкладки: «Слова» —
  добавить слово, «Группы» — создать корневую группу), текущий словарь —
  **host резолвит dictionaryId один раз и раздаёт обеим вкладкам параметром
  слота** (Р8: один курсор словаря, рассинхрон вкладок исключён).
- **ActionMode — только у words** (решение Р2): на вкладке «Группы» action
  mode отсутствует и недоступен (задизейблен); переключение вкладки сбрасывает
  активный action mode (`Msg.ExitSelectionMode` — механизм существует).
  topBar-override нужен только words — контракт вкладки прост.
- Back (В5): вкладки не перехватывают «назад».

Порядок фаз реализации (Р12): данные → domain/group → widget/grouptree
(отдельная фаза, ДО обоих потребителей) → host-рефактор (vocabulary +
wordstab) → groupstab → wordcard.

### 4.2 Use case-слой (Р1)

Use case интерфейсы — в screen-модулях, реализации — в app, **тонкая
делегация** в `CoreDbApi` без валидаций (вся логика «прочитал-проверил-
записал» — внутри `CoreDbApiImpl` в транзакции, §2.4). Чистые функции
`domain/group` (DisplayTree, компараторы) зовутся и из UI-слоёв — Flow и
coroutines в domain не попадают.

## 5. Потоки

- **Вкладка «Группы»:** `groupTree + membershipSlice` → DisplayTree →
  аккордеон (expand — UI-state `Set<GroupId>`); контент слов раскрытого узла —
  ленивая догрузка `wordsContent(ids)` (Р4). Строки слов — тем же виджетом
  item'а, что на «Словах» (В2), read-only: тап → карточка (В6). Создание: FAB
  → корневая (диалог: имя); действие на строке → подгруппа (диалог: имя) (В4).
  Empty-state'ы (Р12): нет групп вообще → empty-state с CTA создать; корневой
  «Все» видна всегда; раскрытая группа без содержимого →
  строка-заглушка.
- **Карточка слова, шапка:** новое поле state + Flow-handler по образцу
  `AvailableComponentTypesFlowHandler` (подписка на `wordGroups`) + Msg +
  effect — 4 новых артефакта, называю явно (Р12).
- **Пикер групп:** плоский список групп с чекбоксами (без «Все»; папок в
  фиче нет — концепт-правка 2026-08-23). Тоггл →
  `addWordToGroup`/`removeWordFromGroup` (направление от факта БД —
  wordGroupIds подписки); **на время записи галочка дизейблится per-membership**
  (Р3, ignore-while-committing — единообразно с контрактом значений), state
  пикера рисуется из Flow базы (ошибка записи → галочка сама вернётся).
  In-flight membership — новое keyed-поле State карточки + completion-Msg +
  правка `hasInFlightCommits`/`isGuardedByPending`: flush-on-back ждёт
  membership-записи так же, как коммиты значений. Два режима пикера (Р12):
  membership-чекбоксы / создание группы с выбором родителя (Д6); дерево может
  обновиться под открытым пикером — state из Flow это покрывает.
- **Удаление группы:** `deleteImpact` → конфирм → `deleteGroup`.

## 6. Публикация (семантика зафиксирована, фича — позже)

Решения П1–П3 ([analysis_sharing_import.md](analysis_sharing_import.md)):

- **П1.** Импорт — всегда в **текущий словарь**; каталог — изнутри словаря,
  фильтр по языку.
- **П2.** Совпадение текста слова (trim + case-insensitive, **Kotlin
  locale-aware**, не SQL NOCASE — Р10д) — сигнал для единого preview-ревью
  (per-word включить/исключить); отказ = слова из пакета нет нигде.
- **П3.** Импортированное слово — **всегда новая строка** (дубли легальны —
  подтверждено кодом: UNIQUE/duplicate-check/text-lookup в проекте нет);
  никакого reuse. Импорт — чисто аддитивная вставка.

### 6.1 Пакет (publishable unit)

Поддерево групп (имена; порядок не хранится — алфавит) + membership + слова +
лексемы + значения + подмножество схемы компонентов (builtin — маппинг по
`system_key` **типов И опций**, Р10г; user-defined; иерархия depends_on) +
метаданные словаря. **Пакет обязан нести пару языков «изучаемый → язык
перевода»** (Р10а): в словаре сейчас только один `numericCode` (изучаемый),
языка перевода нет — витрина по одному коду подсунет пакет с нечитаемыми
переводами; вторая координата — задача фичи публикации (аддитивно).
Audit-колонки и «Все» в пакет не входят. User-state — никогда.

### 6.2 Требования к будущему импорту (зафиксировано сейчас, Р10)

- Preview-ревью резолвит схему пакета **виртуально** (in-memory снапшот до
  импорта): значения пакета ссылаются на типы/опции, которых в БД подписчика
  ещё нет (Р10б).
- Политика импорта значений на **disabled-builtin** подписчика — решить в П6
  (импорт обходит смысл disable — молча включать нельзя) (Р10в).
- Версионный дрейф наборов builtin-опций — П6 (формат/версия пакета).

### 6.3 Отложено до фичи публикации (П4–П6)

Коллизия имён групп при импорте (авторезолв — программный rename), судьба
`quiz_configs`, user-defined типы при импорте, формат/версия пакета,
provenance (аддитивная миграция), сервер/каталог/аккаунты, коллизия входящего
имени с локализациями «Все».

### 6.4 Чек-лист ограничений на v1

1. Не вводить уникальность текста слова; не завязывать логику на текст как
   идентичность (П3).
2. Уникальность имён групп — только UseCase (импорту нужен авторезолв).
3. Самодостаточность словаря: значения — только на пословарные типы (global
   недостижим из UI — гарантия продуктовая; перепроверить при воскрешении
   global-охвата).
4. Идентичность builtin — только `system_key` (типы и опции).
5. «Все» — не строка БД; никакой семантики на локальных id.
6. Язык словаря (`numericCode`) не терять; вторую координату (язык перевода)
   добавит фича публикации.
7. Прогресс — строго в пласте user-state.
8. UUID/provenance/published-флаги в v1 не вводить.
9. Будущая фича IMAGE — copy-in-app-storage + бандлинг ассетов (`content://`
   URI в пакете мертвы).
10. Формат пакета — подмножество формата бэкапа; продублировать в IS488 при
    разморозке.

## 7. Решения (А1–А17)

- **А1.** Три пласта данных, классификация на уровне колонок.
- **А2.** Агрегат — дерево словаря целиком; сборка в памяти; fail-soft orphan.
- **А3.** `dictionary_groups`; uniqueness имён — UseCase; PK `word_groups`
  составной + INDEX(group_id).
- **А4.** Транзакция read-validate-write — целиком в `CoreDbApiImpl`,
  `useWriterConnection { immediateTransaction }`; `core-db-impl` зависит от
  `domain/group`; use case — тонкая делегация (Р1).
- **А5.** `domain/group` zero deps; `widget/grouptree` — общий layout-скелет
  со слотами.
- **А6.** Публикация = снапшот-копия + дубль-модель П3; UUID/provenance в v1
  не вводятся; пакет несёт пару языков (Р10а).
- **А7 (v4, 2026-08-06).** «Все» — единственный виртуальный маркер (заменил
  «Не разобрано»): первый на корне, все слова словаря, счётчик есть (Р6);
  без строки в domain, резерв — все локализации, набор инжектится параметром
  (Р7). Внутренних маркеров нет.
- **А18 (2026-08-06).** Инвариант «папка или лист»: `ParentHasWords` /
  `GroupHasSubgroups` в транзакциях + UI-дублирование (пикер: папки не
  выбираемы; kebab: «создать подгруппу» скрыт у листа). Пустая группа — тип
  по первому действию. Конвертация лист↔папка — будущая фича.
- **А8.** Порядок сиблингов — алфавит, locale-aware Kotlin; `position` нет;
  rename-скачок — принятая цена.
- **А9.** Хостинг: 3 модуля — vocabulary (host) + wordstab + groupstab (Р2);
  контракт вкладки: content + FAB-действие; TabRow в content; ActionMode
  только у words; host раздаёт dictionaryId (Р8); back не перехватывается.
- **А10.** Счётчики = distinct поддерева (В3), у маркеров — их слова (Р6);
  слова в дереве — виджетом «Слов», read-only (В2/В6); контент слов — лениво
  при раскрытии (Р4).
- **А11.** Membership-тогглы: per-галочка дизейбл на время записи
  (ignore-while-committing), state из Flow; keyed in-flight поле в State
  карточки, flush-on-back ждёт (Р3).
- **А12.** `createsCycle` — задел под reparent, в v1 не вызывается.
- **А13.** `membershipSlice` наблюдает три таблицы, включая `words` (Р5).
- **А14.** Normalize имени: trim + NFC + locale-aware case-insensitive
  сравнение; хранится как введено (Р11).
- **А15.** `deleteImpact`: внешние членства — по живым группам; bind-лимит
  покрыт границей «десятки узлов»; DAO-SQL; TOCTOU конфирма принят (Р9).
- **А16.** Порядок фаз: данные → domain → grouptree → host+wordstab →
  groupstab → wordcard (Р12).
- **А17.** ParentNotFound = отсутствует ∪ soft-deleted ∪ чужой словарь (Р11).
