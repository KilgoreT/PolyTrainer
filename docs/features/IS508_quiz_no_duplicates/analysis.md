## 1. Где и почему возникает дубль

`app/src/main/java/me/apomazkin/polytrainer/di/module/quizchat/QuizChatUseCaseImpl.kt`,
`getRandomWriteQuizList` (строки 61–140):

| Строки | Что делает | Где дыра |
|---|---|---|
| 78–89 | грейд-корзины: случайные id по каждому грейду → `getWriteQuizByIds` → `toDomainEntity(type = GRADES)` | — |
| 92–106 | раздача по корзинам в `result = mutableSetOf<WriteQuiz>()` | — |
| 108–114 | добор `leftovers` до `limit`, `filterNot { it in result }` | работает только потому, что `type` у всех `GRADES` |
| 117–126 | «Самые давние»: `getEarliestWriteQuizList(limit, …)` → `shuffled()` → `type = EARLIEST` → `take(2)` | **пересечения с корзиной не проверяет** |
| 127–136 | «Частые ошибки»: то же с `type = ERRORS` | **не проверяет ни корзину, ни «давние»** |
| 138–139 | `result.shuffled()` | — |

`WriteQuiz` — data class, `equals` учитывает `type: QuizType?`. Одна
квиз-строка из корзины (`GRADES`) и из добавки (`EARLIEST`/`ERRORS`) —
для `Set` два элемента; при обеих опциях — до трёх копий. Дедупа по
лексеме нет нигде.

Ревью подтвердило: **других источников дублей нет** — `grade` один на
строку, `getWriteQuizByIds(IN)` отдаёт строку один раз, `@Relation`
одиночные, `QuizGameImpl.loadData` ничего не размножает. `type`
читается только в debug-выводе (`QuizGameImpl.toQuizItem:496`, и лишь
для user-defined компонента).

**Второй эффект бага** (ревью): `QuizGameImpl.saveSession` собирает
апсерты по всем шагам — для дублированной строки два апсерта от одного
исходного снапшота, побеждает последний: один из ответов по слову
теряется, при разных ответах результат зависит от порядка.

## 2. Целевая сборка порции

Контейнер порции — **`LinkedHashMap<LexemeId, WriteQuiz>`** (Д7):
уникальность по лексеме — свойство контейнера на всех путях, ни один
будущий шаг сборки её не обойдёт. Порядок вставки сохраняется,
финальный `values.shuffled()`.

Один общий выбор **`pick(candidates, count)`** для всех трёх шагов
(Д4, мягкое предпочтение слов):

1. жёсткий фильтр: лексема не в порции;
2. проход 1 — кандидаты, чьё **слово** ещё не в порции, в порядке
   списка;
3. проход 2 (только если не набрано `count`) — остальные, без оглядки
   на слово;
4. возвращает реально добавленные (≤ `count`).

Шаги:

- **Корзины:** `pick(bin, expectedCount)`; `remaining -=
  picked.size` — учёт по реально добавленным (раньше `available.size`
  включал бы дубли — при инварианте 1:1 разницы нет, а после Д5 её и
  быть не может). Корзина уже перемешана (`ids.shuffled()`), поэтому
  «первые с новым словом» — случайные.
- **Добор:** `leftovers` = все корзины, `shuffled()`,
  `pick(leftovers, limit − size)`.
- **Добавки** (Д2, Д3): кандидаты = `limit` строк по критерию как
  сейчас → `toDomainEntity(type)` → `shuffled()` → `pick(…, 2)`.
  Порядок `shuffled → pick` сохраняет «2 случайных из
  оставшихся кандидатов». Окно `limit` не расширяется: при полном
  перекрытии добавка даёт 0 — норма (Д3).
- **Лог-маркер** в конце (рядом с `groupFilter=`, тег `###CHAT###`):
  `getRandomWriteQuizList: portion grades=<n> earliest=+<a>/<cand>
  errors=+<b>/<cand> total=<t> lexemes=<u> words=<w>` — `t == u`
  всегда (инвариант контейнера), `w` показывает работу предпочтения.

**Принято по ревью и не меняется:** «выпускники» (`grade > maxGrade`)
в корзины не попадают и приходят только через добавки; пустая порция
(пустой словарь/группа) + опции on — добавки работают как раньше;
`type` у записи-коллизии остаётся `GRADES` (debug-метка «earliest»
у неё не появится — только debug, для builtin «Перевод» метки нет
вообще); две лексемы одного слова с одинаковым текстом компонента дадут
буквально одинаковый вопрос — это данные, фикс не ловит.

## 3. «Частые ошибки» только с ошибками (Д6)

`WordDao.getFrequentMistakes` (`core/core-db-impl/.../room/WordDao.kt`):
добавить `AND error_count > 0` в WHERE (рядом с групповым фильтром
IS500). Сейчас при < 10 строк с ошибками опция добирает слова с нулём
ошибок под видом «частых». `getEarliest` не трогаем: NULL-дата
(никогда не отвеченные) первыми — это и есть «самые давние».

## 4. Unique-индекс `write_quiz.lexeme_id` (Д5)

Сейчас `WriteQuizDb`: `indices = [Index("lexeme_id")]` — обычный
`index_write_quiz_lexeme_id`. Инвариант «одна лексема — одна
квиз-строка» держится построением (`addLexemeWithQuiz` /
`addLexemeWithComponents`; мёртвый `addLexeme(wordId)` выпилен в IS502).

- Entity: `Index("lexeme_id", unique = true)`; `Database.version = 14`;
  экспорт `14.json`.
- **`Migration_013_to_014`** (`room/migrations/`, регистрация в
  `RoomModule.addMigrations`): (1) схлопнуть дубли, если есть —
  `DELETE FROM write_quiz WHERE id NOT IN (SELECT MIN(id) FROM
  write_quiz GROUP BY lexeme_id)` (оставляем старейшую строку; на
  легальных базах — no-op); (2) `DROP INDEX IF EXISTS
  index_write_quiz_lexeme_id`; (3) `CREATE UNIQUE INDEX
  index_write_quiz_lexeme_id ON write_quiz(lexeme_id)`. Имя индекса —
  ровно как в экспорте Room (проверено по `13.json`), иначе валидация
  схемы упадёт.
- По правилу релизов «одна миграция на все фичи релиза»: если до
  релиза появится ещё изменение схемы — оно едет в эту же миграцию.

## 7. Ручная проверка (manual_test.md в Э4)

Детерминированный маркер — debug-статистика первого сообщения сессии
(меню «Show debug»): `### Total: N` считается ДО graceful skip.

- **M1.** Группа IS500 из W = 5 слов с переводами, обе опции on, debug
  on → `Total: 5` (на сборке до фикса — 9: корзины берут все 5,
  добавки дублируют по 2). В логе `total=5 lexemes=5`.
- **M2.** В той группе слово с двумя лексемами при ≥ 5 других словах →
  в сессии один раз (`words == lexemes` в логе); в группе из 3 слов,
  где у одного 2 лексемы, `limit` больше пула → обе лексемы в сессии,
  второй раз ответ совпадает — ожидаемо (Д1/Д4).
- **M3.** Свежая группа без ошибок, опция «Частые ошибки» on →
  `errors=+0` в логе (Д6).
- **M4.** Миграция 13→14 на прод-базе юзера: установка поверх, старт
  без креша, квиз работает; `Total` как прежде.
- **M5.** Большой словарь, обе опции → `Total` 12–14, `total == lexemes`.

## 10. Риски

- Миграция на прод-базах — no-op по данным (дублей нет), только индекс;
  риск — только опечатка в имени индекса, ловится миграционным тестом
  и валидацией схемы.
- Предпочтение слов меняет порядок выбора внутри корзин — на счётчики
  не влияет (пин Э1).
- Baza-кандидат (от ревью): прикладной постфильтр над SQL-топом с
  `LIMIT N` сужает пул и ломает гарантию «взять K подходящих» — либо
  исключение в SQL, либо запрашивать `N + исключений`; здесь осознанно
  выбрано «пул не расширять» (Д3).
