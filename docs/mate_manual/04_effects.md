# Эффекты и роутинг

[← Оглавление](README.md)

## Эффект — различимое намерение

Эффект описывается ДАННЫМИ (data class/object), исполняется handler'ом,
результат возвращается в цикл новым Msg. В результате одного reduce
эффекты образуют **множество** (`Set<Effect>`) — это принцип
различимых намерений:

> Неразличимый дубль намерения не имеет семантики. Если кажется, что
> нужно «два одинаковых» эффекта — они различимы по смыслу, и эта
> различимость обязана жить в данных эффекта (цель, причина,
> порядковый номер, idempotency-ключ).

## Семейства и роутинг

Handler вслух декларирует своё СЕМЕЙСТВО — корневой sealed-интерфейс
эффектов, которые он исполняет:

```kotlin
class WordsEffectHandler(/* ... */) : MateEffectHandler<WordsMsg, WordsEffect> {
    override val effectFamily = WordsEffect::class
    // ...
}
```

Раннер строит реестр «семейство → исполнитель» и доставляет каждый
эффект ровно одному handler'у. Маршрутизация — только по типу
эффекта; логика исполнения (кэш или сеть, ретраи) живёт внутри
исполнителя. Расширение
(лог, метрики) — декоратором handler'а, не вторым handler'ом.

## Громкие ошибки конфигурации

Невалидная конфигурация не живёт молча:

| Ситуация | Когда падает | Ошибка |
|---|---|---|
| Два handler'а на одно семейство | создание раннера | `require` |
| Эффект без исполнителя (сирота) | диспатч | `MateError.OrphanEffect` |
| Эффект матчится на два семейства | диспатч | `MateError.AmbiguousEffect` |

Двойная принадлежность запрещена: эффект живёт ровно в одном
семействе. Подгруппы-интерфейсы ВНУТРИ семейства легальны
(`WordsNavigationEffect : NavigationEffect`) — запрещено лишь
декларировать их как `effectFamily` двумя уровнями.

## Ошибки исполнения

Исключение handler'а не убивает цикл: раннер ловит его и отдаёт в
политику ошибок как `MateError.EffectFailed`. Ожидаемые ошибки до
политики не доводят — handler возвращает fail-Msg. Подробно, включая
отмену и `MateFailPolicy`, — в главе
[«Обработка ошибок»](07_errors.md).

## Каскады

Msg, рождённый эффектом, встаёт в ХВОСТ mailbox'а — FIFO, никакого
depth-first. Наблюдаемость каскада — через
[`MateObserver.onCausedMessage`](08_observability.md).
