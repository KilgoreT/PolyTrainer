# Гайд: как писать сценарии ручных тестов

Спека формата для документов ручного прогона на девайсе (пример-эталон:
`docs/features/IS491_example_component/manual_test_run.md`). Цель — тестировщик
вводит дословно и сверяет, **ничего не сочиняя и не вычисляя**.

Правила ниже — жёсткие. Нарушение = документ переписывается.

---

## 1. Три вида записей, всегда раздельно

В сценарии есть ровно три сущности, и они НЕ смешиваются в одну строку/блок:

1. **Действие** — нумерованный пункт: что сделать.
2. **`ВИЖУ`** — отдельный блок: что на экране.
3. **`ЛОГ`** — отдельный блок: что в logcat.

Запрещено: `Тап в подпись. → списка нет. Лог: count=0.` — это три записи в одной
строке. Правильно:

```
2. Тап в поле подписи.
```
```
ВИЖУ  выпадающего списка нет
```
```
ЛОГ   suggestions: … count=0
```

Стрелки `→` для склейки «действие → результат» запрещены.

---

## 2. Один пункт — одно действие

Каждый нумерованный пункт = **одно** элементарное действие: один тап, один ввод,
одна кнопка. Никаких перечислений действий через запятую.

Плохо:

```
1. Тап по тексту, заменить на «rio», тап в подпись и обратно, затем «назад».
```

Хорошо:

```
1. Тап по тексту значения (откроется правка).
2. Стереть текст.
3. Ввести «rio».
4. Тап в поле подписи.
5. Тап обратно в поле текста.
6. Нажать «назад».
```

Тестировщик отмечает выполнение построчно — длинное предложение через запятую это
ломает.

---

## 3. Каждый шаг и подшаг — с новой строки и пронумерован

Подготовка данных, шаги теста, пункты внутри процедуры — всё нумеровано и по строке
на пункт. Никаких «и ещё сделай то-то» в конце строки.

---

## 4. Блок `ВИЖУ`

- Отдельный код-блок (моноширинный), префикс `ВИЖУ`.
- Перечисления внутри — **по строке на пункт**, не через запятую.
- Пункты «чего быть НЕ должно» — тоже по строке, с пометкой `НЕТ`.

```
ВИЖУ  в списке:
      «Перевод»
      «Определение»
      НЕТ «Пример»
      НЕТ «Часть речи»
```

---

## 5. Блок `ЛОГ`

- Отдельный код-блок, префикс `ЛОГ`. Никогда не в одной строке с действием или ВИЖУ.
- Если лога быть не должно — писать явно: `ЛОГ   value add — НЕТ`.
- В шапке документа — команда фильтра логов и таблица «событие → строка лога».

---

## 6. Данные — конкретные, короткие, без сокращений

- Всё вводимое — дословно в «…». Тестировщик не придумывает значения.
- Слова **короткие и осмысленные**, без аббревиатур. 3–4 буквы — идеал
  (`дом`, `код`, `мир`, `сад`, `sol`, `pan`).
- Аббревиатуры и коды (`IELTS`, `B2`, `T1`) — запрещены: их неудобно вводить и
  читать, и они не читаются как слова.
- Для тестов регистра/дублей брать те же короткие слова в разных регистрах
  (`код` / `Код`).

---

## 7. Реальный UI, сверенный с кодом

- Описывать только то, что реально есть в приложении. **Не выдумывать элементы.**
  Пример анти-паттерна: описали «кнопку Сохранить» в карточке, которой в коде нет
  (коммит там по уходу фокуса). Перед написанием шага — свериться с кодом/экраном.
- Механику фиксации/сохранения/отмены описывать по факту реализации, а не «как
  обычно бывает».

---

## 8. Читается линейно — без ссылок и скролла

Документ читают сверху вниз и выполняют по строкам. **Никаких ссылок на процедуры
в другом месте файла** («см. П-ДОБ», «см. раздел X») — они заставляют скролить туда-сюда.

Повторяемое действие пишется **самодостаточной строкой** прямо в тесткейсе, со всеми
параметрами в ней самой:

```
3. Добавить значение «Стиль»: текст «uno», подпись «Код».
```

Здесь запятые разделяют **параметры** одного действия (что и куда ввести), а не
последовательность разных действий — это допустимо (в отличие от правила §2, которое
про склейку разных действий). Полную атомарную раскладку по тапам давать только там,
где важна сама последовательность взаимодействий (правка, фокус, удаление) — и первый
раз, чтобы показать поток; дальше — самодостаточной строкой.

---

## 9. Выверенные ожидания

- Где проверяется точный счётчик/порядок — заводить **свежий** компонент/данные в
  подготовке тесткейса, чтобы число было абсолютным и не зависело от истории.
- Порядок в списках считать по фактической сортировке (частота, затем алфавит;
  учитывать, что заглавные кириллические сортируются раньше строчных) — и приводить
  готовый ожидаемый порядок, не «отсортировано».

---

## 10. Структура документа

1. **Шапка** — правила чтения (кратко), механика коммита UI, команда фильтра логов.
2. **Подготовка** — что завести до тестов (словари/данные), атомарными шагами.
3. **Тесткейсы** — по разделам; каждый: id + название, «Данные/контекст» при нужде,
   атомарные шаги с блоками `ВИЖУ`/`ЛОГ`. Повторяемые действия — самодостаточной
   строкой, без ссылок на процедуры.
4. **Автоматически покрытое** — сценарии, закрытые androidTest/unit, не дублировать
   вручную; пометить, что покрыто и чем.
5. **Шпаргалка данных** — все вводимые значения и компоненты одним блоком.

---

## 11. Чек-лист перед сдачей документа

- [ ] Ни одной строки «действие + результат/лог» вместе.
- [ ] Каждый пункт — одно действие; нет запятых-склеек действий.
- [ ] `ВИЖУ` и `ЛОГ` — отдельными блоками; перечисления по строкам.
- [ ] Нет стрелок `→`.
- [ ] Все значения дословны; слова короткие, без аббревиатур.
- [ ] UI сверен с кодом (нет выдуманных кнопок/экранов).
- [ ] Нет ссылок «см. процедуру/раздел» — всё читается линейно, без скролла.
- [ ] Счётчики/порядки выверены под данные.
- [ ] Есть подготовка данных и шпаргалка.
